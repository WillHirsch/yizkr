This guide describes the current Wikibase conventions and implementation limits; it does not imply that every approved retained-state capability is implemented. The [provenance diagram](ARCHITECTURE.md#source-and-process-provenance) shows the existing source/run encoding.

## General approach

People, places, artifacts, events and periods can have independent identity where useful. Dates and uncertain intervals use values and qualifiers; not every date needs an item. Ordinary vocabulary additions preserve evidence and identity, while new domain behavior may require code or a migration. The concrete conventions below describe the current implementation, not a promise of arbitrary schema extension without work.

**Retained-state limit:** item creation has durable, instance-qualified bindings and interrupted-write recovery independent of display terms. Entity assignments still depend on one identity map; general incremental addition, assignment migration and retraction remain under #130, #723 and #142. Preserve the existing guards; a retained instance must not be reset to bypass them. See [recovery and its boundaries](ARCHITECTURE.md#item-creation-and-interrupted-write-recovery).

- The schema is self-describing: properties and classes are minted as Wikibase properties/items in-instance.
- Mirror Wikidata property _semantics_ where a good equivalent exists (instance of, date of birth, spouse, residence, depicts, coordinate location, start/end time, stated in...), using local P-ids. The vocabulary is declared in `src/yizkr/model/manifest.yaml` and minted by `yizkr bootstrap`, which maintains the mapping table (local id – Wikidata id) on the wiki page `Project:Model mapping`. Local P/Q ids are per-instance and never recorded in the repo.
- Every entity gets a label and a short description; name variants go in aliases. English labels are the bootstrap's idempotency key: a property's and a manifest vocabulary item's label names one entity alone, and renames must happen on the wiki and in the manifest together. Other items may share a label: two people of one name are two items under one label (homonyms). The wiki client's label index gives such a label the numerically earliest of its items, and keeps every holder, and fails only where a label must name one item alone: a vocabulary item's (the vocabulary's whole read, the bootstrap) and bootstrap lookups that require a unique vocabulary label. The vocabulary is read bounded where it can be (#507): the ids `Project:Model mapping` gives the manifest's labels, each checked to carry its label, 50 a request. That read sees only those ids, so another item under a vocabulary item's label goes unseen there, and the bootstrap, which reads every label, refuses it. When the page is missing, lacks or repeats a manifest label, names one id under two labels, or an id is missing, a redirect or carries another label, the vocabulary reads every label whole. No extracted entity is found by its label (#109): the writer uses its identity-map operation and verified server binding (below).
- **Current mapping: one item per cluster of the identity map.** Every local mention must belong to the supplied map; otherwise the writer refuses the batch before mutation (`UnmappedMention`). An approved equivalence can name an existing QID explicitly. Reviewed batches use the original extraction as `mapped_from`, so dropping claims does not change which mention a local ID denotes. A cluster creation operation reserves an opaque entity ID and binds it to the resulting QID in the shared server registry. Repeating the same operation reuses that binding after label or description edits. The initial label comes from the cluster’s mentions; other names become aliases, and each source can contribute referenced kinds or type hints. Rebuilding disposable state establishes a new deployment generation and does not promise stable QIDs.
- **Current writer limit: one identity map per deployment generation.** The registry reserves the map hash in an immutable server record before mapped entity writes. Run labels and descriptions also display map provenance, and the writer retains its checks for other recorded maps. A changed map requires verified assignment migration under #130; matching generated terms cannot migrate a cluster. `ingest run` builds one map over its available batches and refuses unmapped mentions. Scratch reset/reuse guards remain, and explicitly disposable fixtures can disable the one-map restriction for isolated tests. Display collision rules still distinguish extracted entities from registered artifacts, vocabulary and process items; those rules do not establish identity.
- An extracted entity’s initial `wbeditentity` request includes its label, description, aliases and sourced kind/type hint. Its creation revision carries the reserved intent marker. A lost response can leave a completed item: recovery verifies that revision and records the QID receipt before continuing. Registration and process items that require their own QID for self-references finish those statements separately on resume. No multi-item batch is atomic.
- **An item’s initial description is its cluster’s source descriptor.** It describes the kind and the sources naming it, such as `human named in a genealogical report` or `human named in 3 sources`. Same-named clusters receive deterministic ordinal suffixes to satisfy Wikibase’s label/description uniqueness rule. Descriptions contain neither extracted biographies nor artifact titles, QIDs or digests. They are display text: the registry supplies identity, existing curator descriptions remain unchanged, and an unbound item with matching display terms triggers migration refusal rather than adoption.
- Wikibase keeps labels, descriptions and aliases trimmed and normalized, with a 250-character limit. The writer normalizes new display terms, fits long terms with a digest suffix and avoids a description identical to its label. Registration and alias hygiene use the same term conventions. These transformations do not change a bound entity’s identity; lookup uses its creation binding. Statement values retain their own validation and comparison rules.
- Wikibase puts a term, and every text, in NFC by the tables of Unicode 15.0 (ICU 72.1 in the wikibase/wikibase:7 image), and the writer by Python's (14.0.0 on Python 3.11). Unicode's normalization stability policy makes the two agree on every text whose characters Python's tables assign, so the writer sends no term that holds a character they do not, noncharacters aside, read whole, past the cut too, so that no cut of such a term is sent either: a combining mark assigned since, such as U+1E08F, the combining Cyrillic Byelorussian-Ukrainian i, may take another place in the instance's NFC. An alias or a type hint that holds one is left out, never changed, and the write's result names it in `refused_terms`, with a warning. An entity's description is the writer's source descriptor, made of manifest keys alone (above), so no description is named (#86). An entity whose label holds one is neither found nor minted, and each claim that mentions it is refused. The registrar makes no alias of a title that holds one, and content-tags a new item's label made from one, as it does a taken label, so two same-named copies stay two items whatever form the instance keeps the first one's label in. A claim refused for its text, as a misplaced document subject (ADR-0035 §3.4), or with an entity that may join neither the item under its label nor the one under its tagged label (ADR-0010), mints nothing. A manifest record whose local refs only such refused claims hold has nothing of it sent, so its aliases and type hint are not named in `refused_terms` either (amended by #444, 2026-10-03). A run item's label holding one, an extraction run's or the place-hierarchy pass's, or an extraction run's description, raises ValueError before the run item is looked up, and so before anything is written, so unsupported display terms never reach the graph. The interpreter's tables must be no newer than the instance's, which a unit test checks (writer's INSTANCE_UNICODE; ADR-0010, #431).
- The current bootstrap references schema-level statements (such as the subclass hierarchy) to the _model manifest_ item representing `src/yizkr/model/manifest.yaml`. The approved provenance policy requires accountable origin and versioning for schema and operational records; it does not require every such record to use a source-artifact citation. This encoding remains until a supported replacement is implemented (ADR-0003).

## Core classes (items, via "instance of")

- human
- place
- time period (linked to PeriodO definitions where applicable)
- event (migration, military service, a wedding with its subclasses civil wedding and religious wedding, a divorce, an annulment; birth and death classes are available for curator-made events, not extraction — ADR-0036, ADR-0040)
- partnership (a couple's relationship of any kind, for two people a source presents as a couple without saying they married), and its subclass marriage (Q8445): each is an entity, not an event. Its couple are participants with the role `partner` or `spouse`; `started_by` links its wedding and `ended_by` a divorce or annulment (ADR-0036). `ended_by_death_of` links the partner whose death ended it, only where the source states that they were married when that partner died. Otherwise views derive the end without writing one (ADR-0040).
- artifact (subclasses: photograph, certificate, letter, census page, newspaper clipping, presentation, genealogical report, address book, ...)
- organization (an agent — company, bank, committee, government body, school, congregation; distinct from place — see ADR-0012)
- family (a named family or household unit — ADR-0014)
- vessel (a ship; e.g. an emigration vessel — ADR-0014)
- legal instrument (a cited law, decree, gazette, or register — ADR-0014)
- military unit (a regiment, brigade — ADR-0014)
- occupation (values of the `occupation` property; labels keep the source's wording)
- unclassified entity (the open-schema holding class — see ADR-0013)
- artifact fragment (a page, crop, or region of an artifact)
- extraction run (one pipeline execution: model name+version, date, prompt/pipeline version, software commit)

**Manifest descriptions are extraction-prompt surface**, not only documentation. Every property and item in `src/yizkr/model/manifest.yaml` carries a description, and the extractor is shown it verbatim beside the key: a property's description is what tells the model which way a relation points (`employer` takes the organization, not the employee) and what kind of entity the value must be (`location` takes a place). Write them for that reader as well as for a human.

Items flagged **`entity_kind: true`** are the kinds the extractor may type a document-mentioned entity as (the ADR-0007 manifest pass), and the prompt renders that set from the manifest rather than restating it. Artifact types, controlled-vocabulary values (`circa`, `male`), and infrastructure classes (`artifact_fragment`, `extraction_run`) are real classes but not entity kinds. A new item is not offered to the extractor until it says so. The classes of entities that are no entity kind, `artifact` and the artifact types, `time_period_class` and the infrastructure classes, are marked **`entity_class: true`**; with the entity kinds they are the manifest's **kind keys**. The manifest does not load when an item in the subclass hierarchy is neither, or when an entity kind is also marked `entity_class` (amended by #462, 2026-10-05). A controlled-vocabulary value is neither. Outside the hierarchy nothing else tells a class (`time_period_class`) from a value (`circa`), since each may be the one item its property accepts, so the mark there is the manifest author's to set, and a test pins the classes it holds.

**Controlled vocabulary values** (items, never entity kinds): `circa`; `male` and `female`; the participant roles `principal`, `partner`, `spouse`, `witness` and `officiant` (`object_has_role`, ADR-0035 §3.2); the kinship classes `kin_parent` … `kin_relative` and the sides `paternal` and `maternal` ("Kinship" below); the civil statuses `unmarried` (never married), `married`, `widowed` and `divorced` (`civil_status`, ADR-0035 §3.1); and the five judgement note categories `judgement_kind`, `judgement_relation`, `judgement_date_reading`, `judgement_identity` and `judgement_other` (ADR-0035 §4). The kinship classes whose word is also a role's or a property's (parent, child, sibling, relative) carry "(kinship class)" in their labels, so that no two items share a label (the bootstrap's key) and none reads as the property of the same name.

Current birth, death and parentage conventions (ADR-0040):

- `birth` and `death` stay classes, for events a curator makes, but are kinds no extraction makes. Validation refuses an entity of either kind, and the GEDCOM adapter makes none. A birth and a death are statements on the person ("Living persons and privacy" below).
- The `parent` and `informant` roles are retired: `object_has_role` does not accept them and no prompt offers them; their vocabulary items stay.
- Step relationships use `kin_step_parent`, `kin_step_child` and `kin_step_sibling`.
- The qualifier `parentage` takes `parentage_birth`, `parentage_adoptive` and `parentage_foster`, labelled "birth (parentage)" and so on, since the `birth` class owns the label "birth" ("Kinship" below).

**The relation decides the kind (ADR-0031, ADR-0035 §3.5).** Every item-valued property declares `accepts` in the manifest: the kinds its value may be (`location` a place, `carried_out_by` an organisation, `participant` a human or a family), each named exactly, so a subclass is accepted only where it is listed; or `any` (`depicts`), `subject` (the subject's own kind, for `said_to_be_the_same_as`) or `class` (`instance_of`, `subclass_of`). A list that names an entity kind also names `unclassified_entity` (ADR-0013). The manifest does not load when an item-valued property declares none. Validation refuses a claim whose value is of a kind its property does not accept, and extraction counts it among its rejects. An existing item named by its QID has no kind in a batch and is not checked. A vocabulary ref to a kind key (`human`, `place`, `time_period_class`, `photograph`) names the class, not an entity of it, so only `instance_of` and `subclass_of` take one, and they take no controlled-vocabulary value (`circa`); `depicts` (any kind) and `said_to_be_the_same_as` (the subject's kind) take no vocabulary item at all. An item value is thus an entity of the batch, an existing item named by its QID, or a vocabulary item its property names. Nor is an item value, a claim's or a qualifier's, ever the claim's own subject (the same local id, the same QID, the same vocabulary item, or a local ref resolved to the subject's QID): no property of the manifest takes its subject as its value, so Flörburg `location` Flörburg and Sebastian his own `father` are refused and counted among extraction's rejects. The claim is the unit of rejection: a qualifier naming the subject rejects its whole claim. The GEDCOM adapter leaves out a family's link that makes a parent their own child, and counts it (ADR-0036). (Amended by #461 and #462, 2026-10-05.) The writer checks the same rule again before its first write, since the identity map, an approved equivalence or a curator's correction of the equivalence sheet can put a claim's subject and its value, two mentions, on one item after validation: a father and a son of one name that clustering merges, with a `father` claim between them. A claim whose value or qualifier's value is then its subject's item is refused whole, nothing of it written, the rest of the batch written; the writer's result names it in `refused` and again in `self_references`, as `ingest run`'s write step record does, and the scratch write's record, the run report (`content.write.claims_self_referencing`) and the run-to-run diff count these apart from the writer's other refusals and from extraction's rejects. (Amended by #491, 2026-10-16.) A `time_period` claim from extraction is, for now, a counted reject: `time_period` accepts only a period, an entity of `time_period_class`, no entity kind offers one and no QID exists before write. `country_of_citizenship` accepts a place, since the place model has no country class; its description, which the chunk and single-pass prompts carry, says the value is a country, never a town, city or region within one, and validation does not tell them apart. The entity-manifest and chunk prompts name it among the relations of place, and the manifest gives the country a source states as a person's citizenship as a place entity, whether the source names it or gives only an adjective of nationality. A country given only by an adjective is labelled with the adjective as written (_an Australian citizen_ gives the place "Australian"), with the record status `adjective`, which keys nothing: the adjective is never turned into a name of the country, which would add a word the source does not write and pick one state where the source gives a nationality (ADR-0035, amended by #573). `part_of`'s list is flat for now: it takes a place or an artifact whatever its subject, so a place `part_of` an artifact passes the check, which reads the value alone.

**Reference properties** (`stated_in`, `inferred_from_extraction_run`, `judgement` and `judgement_note`) are marked `reference: true`: validation refuses them as a claim's or qualifier's property, and no prompt offers them. `offered: false` also keeps a property out of prompts while retaining it in the manifest and bootstrap; the scratch-run marks use this (`scratch_run`, `run_manifest_hash`, `identity_map_hash`).

**Document and placed subjects (ADR-0039).** The seven `document_subject` properties are `issued_by`, `author`, `addressee`, `inception`, `location_of_creation`, `main_subject` and `shows`. Their subject can be the source artifact itself, an artifact that source places, a batch entity of an artifact kind, or an `unclassified_entity` that is the source's mention of an artifact. A document-subject claim about anything other than its own source requires an excerpt conveying the fact. Extraction cannot create artifact-kind entities or classification claims; a structured adapter or hand-written batch can supply them. Thus a GEDCOM media record can state its un-held media item's `inception`, and the 1958 letter can state its enclosed certificate's `main_subject` on a mention item.

An approved equivalence can resolve such a mention or artifact-kind entity to an existing item. Each claim retains its own pre-confirmation subject in `confirmed_from`, including its kind; validation and the writer accept the QID only for those allowed forms and check any corresponding confirmed entity record. An outright QID subject without that record remains refused. This supported resolution mechanism is not a general durable identity or merge/split workflow.

The `placed_subject` property `caption` takes only an artifact that the source places. Validation receives the bound owners that a PDF or PPTX transcription's located source context places on a page or slide, and the image markers of a standalone reading's pages; the writer separately checks the source's registered placed media. An artifact subject on any other property, a disallowed subject form or a required excerpt that is absent is refused. The [shared source consumers](ARCHITECTURE.md#shared-source-consumers) take this placement context from the common inventory; the [ingestion contract](INGESTION_CONTRACT.md) defines the shared source/evidence boundary.

`yizkr ingest write`, `yizkr claims --validate` and `claims.py --validate` take this context with `--placed`: a container's verified `container-inventory.json` or its directory, an explicit `derived-media.json` compatibility record, or `<source>=<sha1>[,<sha1>...]`. A directory holding a common inventory is read from it alone, and an invalid one is refused rather than replaced by an older record. The write also needs registered items carrying those media hashes. Without the context, claims requiring a placed subject are refused; the command explains how to provide it.

**A retired property** stays in the instance and takes no new claim: it accepts nothing, validation refuses every claim of it, and no prompt that the manifest renders offers it. `spouse` is retired (ADR-0036): the spouse link is derived from a marriage's participants. The GEDCOM adapter makes marriages and partnerships (ADR-0036 §5, "Marriages, residences and other periods" below), so no batch carries a spouse claim. The writer refuses one itself, since `yizkr write` takes a batch without validating it: a claim of a retired property, or of a reference property, as its own property or a qualifier's, is refused before the first write, named in the result's `refused` list with a warning, and the rest of the batch is written (#410).

## Reference pattern (see ADR-0003)

The approved policy distinguishes historical assertions, curator attestations, derived results and operational metadata. Each needs provenance appropriate to it (ADR-0003). The current claim schema and writer still require source artifacts and implement the following encoding; broader provenance and history support follows the [ingestion contract](INGESTION_CONTRACT.md) and remains implementation work.

Historical statements on the current claims path carry a source reference with:

- stated in → artifact item (or artifact-fragment item)
- locator qualifier(s), where reliably known: page number and/or a region given as a percentage bounding box "x%,y%,w%,h%". IIIF canvas/region URIs are an optional future representation (ADR-0004), not an implemented requirement of the claim schema
- the printed page number, where there is one: the page number printed on the page the `page number` locator names, exactly as printed (`printed page number`, a reference property). The page number stays the physical page, the page's place in the media from 1, so a claim read from page 6 of _Our Family from Germany_, whose sixth page is printed as page 4, cites `page number` 6 with `printed page number` 4. The extractor sets it from the transcription record (ADR-0037), never from the model: only for a claim whose page number is one physical page whose record gives a printed number. A range, a page given in words, a page the record gives no printed number and a transcription with no record (a text file's, a deck's slides) get none; none is ever guessed (#424). It describes the physical page: a page that shows a spread with one half numbered keeps that one number for every claim read from it, as both ways of reading a PDF give it the same (ADR-0037 §2). The claims review sheet shows it in a `printed_page` column beside `page`, empty where the reference has none; like the other locators it is shown for checking and never read back, so a curator's edit to it is ignored (#449). A source that gives a printed page number gives its page number too: validation refuses one without the other, in a prepared claims file as in an extractor's batch. An excerpt's claims read the excerpt's own transcription, so they never take the printed number of the page that places it, and its `part of` the container keeps the container's physical page (ADR-0008)
- the source part, for a claim read from a PDF or PPTX or from an excerpt of one: one `source part locator` (a reference property) per structural placement of the part that supports the claim, or one for the part where it has none. Each is a compact JSON string naming the container's SHA-1, the inventory's source-part and placement identities, the part's kind and page or slide, and, when known, the digest of the reading it was located in. Extraction assigns it from the reading's located source context, never from the model; the inventory resolves it to the native part. A locator is never cut to the text limit. Repeated placements locate one source; they are not further witnesses
- optional short transcription excerpt supporting human verification, tagged with the language it is written in (BCP-47). `yizkr ingest run` takes each document's language from its transcription by default (`--language auto`, ADR-0015): from the transcription record the vision engine fills, which names the languages each page is written in (ADR-0037), and otherwise by detection from the text outside its editorial marks. So a mixed-language folder tags each excerpt correctly; the extractor may still tag individual excerpts in their own language (a quoted passage in another tongue)

Machine interpretations on this claims path add a process reference:

- inferred from extraction run → extraction-run item
- with, where the claim carries a **judgement note** (ADR-0035 §4), `judgement` (the item of its category) and `judgement_note` (its sentence) beside it, in this run block alone: never in the `stated in` block, never as a qualifier, never on the run item. An entity's note, a kind or an identity call, goes in the run block of the `instance of` statement the writer writes, or adds a reference to, for its item. A note's sentence goes in NFC, on one line and cut at 400 characters as a locator is (below), and never refuses its claim; one that holds nothing the instance keeps, or a character Python's Unicode tables do not know, is left out with a warning, and its claim written without it, as every note is, with one warning, on an instance whose vocabulary lacks a note term. A curated claim has no run block, so no note. The write's result counts the noted run blocks it added (`notes_written`, #410), which the scratch write stage records for each document and the run report sums

A statement whose `sourcing circumstances` records what its source says of its own making (`machine-assisted`, ADR-0008, #666) adds a third reference: `stated in` the same artifact, with the page number, printed page number and transcription excerpt of the source's statement about how its text was prepared. It is the marker's evidence; the claim's own source block is unchanged.

On the claims path, a value asserted more than once, by several artifacts or by one artifact in several places (two pages, two passages, two regions of a scan), is one statement for each set of qualifiers. It carries a `stated in` reference for each place, with that place's locators and excerpt, and the run reference of each run that added one, one block for each of its notes (and one without a note, where a claim of the run gave none); writing a batch again adds no reference (#335). The run block is compared whole, with its note: a second claim of the same run on the statement adds its own run block where its note differs, so one statement can carry several blocks of one run, and a reader counts runs by run item, never by blocks. A claim from a place the statement already cited before the write adds its run block only when it carries a note, or when a noted claim of its run gave the statement a block of that run, in this write or an earlier one. A statement is compared as a curator's when it was one before the write and still is: a machine claim of the write that joins a curator's own write at normal rank makes it a machine one for every claim of the write, while one whose rank a curator changed stays a curator's. The artifacts it cites for that comparison (below) and the places it cites are read as it stood before the write, and a claim that adds nothing is looked at again once the batch's other claims are written and its kinds recorded, so a run's noted and note-less claims, and a curator's claims beside machine claims, from one place or several, give the same blocks in whatever order the batch gives them, for the run that wrote the statement and for a later one, and a later run's note-less claims alone add nothing there (#410). An entity's kind takes its run blocks by the same rule. No block is edited to add or remove a note. The exception is a statement with no run reference (a curator's own write, until a machine claim of this write or an earlier one joins it) or whose rank a curator changed: the writer adds nothing to it for another place of an artifact it already cites (the writer's module docstring, `src/yizkr/pipeline/writer.py`, gives the rule). The kinds and type hints the writer records after the claims, from an entity manifest or a ref, follow ADR-0007 instead.

Wikibase holds at most 400 characters in the text of a string, external-id or monolingual text value, a reference's page number, printed page number and region among them, and no text value with a line break or a tab in it, or whitespace at either end; it refuses the whole edit that sends a text it does not hold. It also cleans a text up, making each C0 control character but the tab, the line feed and the carriage return, and each of the noncharacters U+FFFE and U+FFFF, U+FFFD: in a string or external-id value before it checks and stores it (so it changes a vertical tab or a form feed there, and refuses one in monolingual text), and in every text its API gives back, monolingual text included. The writer checks each text in NFC, the form the instance keeps it in, and sends none that the instance would give back changed (#366, #384, #403). A page number, printed page number, region or excerpt goes on one line: whitespace at either end is dropped, a line break inside becomes " | ", a tab a space and each other character the instance cleans up U+FFFD, as the instance gives it back, so a re-run finds its reference block; one of whitespace alone is left out. One still over the limit is cut at a break between words and ends with " … sha1 " and the first 12 hex digits of the SHA-1 of the whole text: a locator only places the claim in its source, as an excerpt only helps a reader check it there, and the digest keeps two places whose locators or excerpts agree up to the cut two references. A claim whose own text, its value or a qualifier's, is over the limit, or holds a line break or a tab, or has whitespace at either end, or holds a character the instance cleans up, or holds a character Python's Unicode tables do not know (above; its page number, printed page number, region or excerpt holding one refuses it too, #431), is refused, never cut, trimmed or cleaned up, since that would alter what the source says: nothing of it is written, and the write's result names it by its claim id (its review-sheet id, unless the review corrected it), with a warning that says why (the writer's module docstring). Every other claim of the batch is written. An entity's type hint is free text, compared ignoring its spacing, so it goes with each run of whitespace in it as one space, and each character the instance cleans up as U+FFFD, and a re-run finds the statement written for it.

The current writer's curator-attributed statements (a value correction from the review CSV) carry the `stated in → artifact` reference only: the human decision is recorded in the reviewed artifact and MediaWiki edit history, rather than a machine run block. The pipeline marks these with the claim contract's `curated` flag, which only the review sets: an extractor drops the flag, and any row approval, from a model's answer, so every claim a model gives is written with its run reference.

The pipeline's claim JSON contract implementing this pattern is `src/yizkr/claims.py` (`ClaimBatch`): sources are required fields there, ranks are unrepresentable, and property/item references use manifest keys resolved to local ids only at write time. A claim cites its source artifact by content: the SHA-1 of the artifact's media (`ArtifactRef`, see _Artifact identity_ below), which holds across instance resets. It is the only form a source takes: a batch whose claim names its artifact item by QID does not load (#102). The writer resolves the hash to the artifact item carrying that `media SHA-1` at write time, and refuses a batch that cites media no item carries before it writes anything. So an artifact a claim cites has media: a page fragment is cited through its artifact and a `page number` locator, and an un-held GEDCOM media item (below) is never a claim's source. Every producer names the source itself: an extractor sets each claim's source to the key of the document it read, whatever the model wrote there; the GEDCOM adapter cites the export's bytes; and a face proposal cites the photograph's bytes, while its subject stays the photograph's item. No transcription and no extraction prompt names an artifact by QID: a transcription names its artifact by the same key, and the extraction prompts name it by that key and ask the model to cite it (#127), so a reset, which gives each artifact a new QID, changes neither.

## Correction and review

The current contract permits audited correction, supersession and retraction of erroneous interpretations, duplicate representations and attribution mistakes while preserving genuine source disagreement. It distinguishes approval to retain from approval to publish. Bounded sets of ordinary assertions may be approved together; identity changes must be explicit in the review, and existing-entity merges/splits and face associations require affirmative confirmation.

The writer currently adds claims and references and respects curator ranks. Review CSVs can correct claim values and resolve approved equivalences, but they do not supply a general retained-state correction/retraction/recovery interface. Unchanged approvals should survive unrelated additions; materially changed content, attribution or assignments require scoped review. The [ingestion contract](INGESTION_CONTRACT.md) defines durable history and affected-change handling; #130 and #142 implement it. Keep current enforcement until those replacements are implemented and verified.

## Artifacts and registration

- Current storage: media are wiki files on the instance; the artifact item points at its file page via the `media file` (string) property (ADR-0004).
- **A file's name is in the form MediaWiki takes as it is** (ADR-0010 as amended by #373, after MediaWiki 1.45.4's source). A file is uploaded under its own name, and a medium a container embeds under `"<container title> <its name>"`: every letter kept, each character MediaWiki refuses in a file name made `-` (`# < > [ ] { } |`, `: / \` and the controls other than whitespace), as is the start of each sequence it refuses (`%` and two hex digits, a character reference such as `&amp;` or `&Сартина;`, `~~~`), each run of whitespace and underscores one space, a `-` before a dot that would start a part (`.jpg` is `-.jpg`), and the dot before each part but the last that MediaWiki refuses as an extension made `-` (`Hutmacherei.com.pdf` is `Hutmacherei-com.pdf`; a refused last part, the file's type, is left, and MediaWiki refuses the upload). A name these rules leave nothing of leaves the title as the name, or, with none, is `-`: never empty. At most 231 bytes in UTF-8: MediaWiki's 240, less the 9 a content-tagged name adds. A longer name is cut, never between a letter and its combining marks, with "…" where the cut is: the title first, so the medium's own name stays whole; then the title left out, so a name that fits on its own is never cut; and then the name before its extension. A `media file` names the file as MediaWiki stores it, its first letter a capital.
- An artifact's description is put in the stored form, then cut, ending in "…" and never between a letter and its combining marks, to the 250 characters Wikibase takes: the one registration writes, ``"ingested by `yizkr ingest run` from <file name>"`` (`yizkr scratch run` in a scratch run, #200), passes that for a long file name (ADR-0010 as amended by #373).
- Registrar statements (`instance of`, `media file`, a fragment's `part of` + page qualifier) are referenced `stated in -> the artifact item itself`: an artifact asserts its own kind and composition by existing. Extraction-run items use the same convention for their `instance of`. These registrar/writer paths currently write only referenced statements; that is their implemented encoding, not a requirement that every operational record use an artifact citation (ADR-0003).
- **A run item states its kind in a second write.** Its `instance of → extraction run` cites its own QID. The initial item creation therefore precedes its self-reference. Resume verifies the operation’s creation binding, even after a display edit, and completes any missing kind or run marks on that same item. Existing curator ranks remain unchanged. The extraction and place-hierarchy paths share this recovery mechanism; a matching run label without a binding requires verified migration.
- **A scratch run marks its run items** (#200; ADR-0025 §1). The run item of each batch a scratch run writes states, in the same second write as its kind and stated in itself, `unratified scratch run → <run id>` (the run that wrote it: nothing it backs is ratified, reviewed or confirmed, and the next reset discards it), `run manifest hash →` the SHA-256 of the settings its run manifest records, and `identity map hash →` the SHA-256 of the identity map the batch was written with. The three are string properties of a run item alone, marked `offered: false` in the manifest, so no prompt offers them: the extraction prompts list only the properties a claim may use, and the critique prompt only those the manifest offers (decision EZ), so every prompt is as it was, byte for byte. A run item found again lacking one gains it; one it states already, at any rank, is left as it is. The LAN site reads them: when any run item states `unratified scratch run`, every page's header says the instance holds a development-stage scratch run and names it.
- **A scratch run writes unattended** (#200; ADR-0025 §1, §2). Its write stage takes every claim of each document's batch, with no review and no approval file, at normal rank, with both references, through the run's one identity map, on an instance the run reset itself; depicts claims are left out of what the writer is given, and counted in the run report, so no scratch run writes a depicts statement (ADR-0005). Each claim's write has the edit summary `scratch run: write unratified claim`, and each artifact's description names `yizkr scratch run` as what ingested it.
- **Registration is part of the write** (ADR-0025 §2; ADR-0010 as amended by #103). `ingest run` registers a document just before it writes the claims that cite it: its artifact item, its page fragments and a deck's derived media, each found or made by the SHA-1 of its media. Nothing before the write has an artifact item, and a write that runs again (a changed review, say) registers again, finding by SHA-1 what the earlier write registered.
- **An item that may be an older artifact is flagged, never adopted** (ADR-0010 as amended by #371). An item with no hash has no `media SHA-1` and names a `media file`, as an artifact registered before content hashing does, or is an `instance of` an artifact kind, as a GEDCOM media object's item is (a label, no file). Each time registration makes or finds an artifact or derived medium while another item names a wiki file holding its bytes (`shared-file`), or while its title, or its own label before its content tag, is an unhashed item's label (`unhashed-title`), `ingest run` raises the flag as an alert of the write naming the items by QID, for a person to look at; it repeats on every write until a curator acts on the older item. A new item is made as any other, and neither item is changed. Registration writes `media file` and `media SHA-1` together, so a reset instance never raises `shared-file`; it raises `unhashed-title` only for an artifact or derived medium registered under exactly a GEDCOM media object's label, or with a page fragment under it, whichever is written first: a GEDCOM written after the artifact never joins its media object to it, or to its fragment, by the label, but makes it an item of its own, labelled `"<label> [media object]"`, and its write raises the flag, on every artifact registered under that label, content-tagged or not (ADR-0010).
- **An item takes its label on its own side only** (ADR-0010 as amended by #444 and #109). No entity joins an item by its label: each cluster of the identity map is its own item (above). A media object, or any artifact-kind entity, takes the label of an item with no hash that is an artifact or a part of one, or a label nobody holds; a person, a place or any other entity never takes the label of an artifact or a part of one. One that may not take its label takes an item of its own under its label tagged `" [media object]"`, or, whatever its kind or none, `" [not an artifact]"` (one tag for every kind; amended by #444, 2026-10-03), its name an alias; one that may take neither label is refused, with its claims, before the write.
- **A page fragment is keyed by its artifact.** The fragment for page _n_ is the item that is an `instance of artifact fragment` and `part of` the artifact with `page number` _n_, whatever its label. A new one is labelled `"<artifact label>, page <n>"` (content-tagged if that label is taken, or if it holds a character Python's Unicode tables do not know and bears no tag yet; the artifact's label cut to end in "…" if the whole would pass 250 characters) and made in one write with both statements, each stated in the artifact. So same-titled artifacts never share a fragment, and a derived medium, `part of` its container with a page qualifier too, is never taken for one.
- Machine-proposed entities (people, places) get their `instance of` statement referenced to the artifact that mentions them. A later source that names the entity adds its own references (the artifact and its extraction run) to that statement, or, when it gives a different kind, a statement of its own: the kinds different sources give coexist like any other attributed values (ADR-0002, ADR-0007). A `type hint` accumulates the same way, compared as free text.

## Artifact identity (see ADR-0010)

- An artifact's identity is its **content**, not its filename. Every artifact with media carries a `media SHA-1` statement (hex SHA-1 of the bytes), referenced `stated in → the artifact itself` (for media derived from a compound artifact: `stated in → the container`). The registrar keys on this hash alone — identical bytes are one artifact item however they are named, and an alternate filename becomes an alias unless it is another item's label. A title never finds an item: two files that share a title are two artifacts, and media without bytes to hash cannot be registered. Bit-identical media is never stored, itemised, or extracted twice.
- When a title is already another item's label, the new artifact's label is disambiguated with a short content tag (`"<title> [<sha1[:8]>]"`) rather than colliding. Titles are compared and set in the form Wikibase stores labels in, by the rule the writer keeps labels by (above: trimmed, then U+FFFE and U+FFFF made U+FFFD, then NFC; #369, #403), an artifact's description goes in that form too, and a title longer than the 250 characters Wikibase takes, as it is or once tagged, is cut to fit, ending in "…" (#371). The tag is a label convention, no longer one the label index needs (#94), and which homonym bears it depends on registration order: nothing may key on an artifact's label, only on its `media SHA-1`.
- A file on the never-ingest list is never registered or uploaded, and neither is a medium a container embeds that the list names: a deck's medium by any of its names in the archive or by SHA-1, a PDF's image by SHA-1 alone, since its names are its places in the PDF ("page 6, image 1"), not files (ADR-0008). A glob that names a deck's image names its SHA-1 in every container that holds those bytes (#620). The container's own file is uploaded as it is, with whatever it embeds.
- **Every `media file` holds the bytes its item's `media SHA-1` names.** A wiki file is never overwritten: bytes whose file name already holds different bytes are uploaded under a content-tagged file name, `"<stem> <sha1[:8]><extension>"`, and bytes the wiki holds already reuse that file (ADR-0010, "Media files").
- **Near-duplicates are not identities.** Re-encodings, re-scans, and crops have different bytes and are (for now) distinct artifacts; linking confirmed alternate versions is a curator judgement through a future review queue and a `version of` relation (ADR-0010), never an automatic merge — the same rule as person identity (ADR-0007).

## Organizations (see ADR-0012)

- An `organization` is an agent — a company, bank, committee, government body, school, or congregation. It is **distinct from `place`**: an organization has a `location`, it is not one. **The relation decides the kind** (ADR-0031): a relation of place (born, died or buried at, lives at, located at, deported to, held at, a citizen of) takes a place, and a relation of agency (`issued_by`, `carried_out_by`, `employer`, `educated_at`, `member_of`) an organization. So a camp, a prison, a hospital or a school named only as where something happened is a place, and one the source shows acting is an organization: the registration card's Peiltal court prison, where Leopold was held, is a place; the Landgericht Rekau, which divorces Leopold and Agnes, is an organization. Where one source uses one institution both ways, it gives two entities, a site and a body, linked by the organization's `location`. The extraction prompts carry the rule, and validation refuses a relation whose value is of a kind it does not accept.
- `issued_by` (P2378) links a document to the organization that issued it, such as the register office of a certificate. Its subject is the document itself: a claim names it by the SHA-1 of its media, as its source is named, and the writer writes the statement on the artifact item (ADR-0035 §3.4). The other document-subject properties (`author`, `addressee`, `inception`, `location_of_creation`, `main_subject`, `shows`) take the document as their subject the same way (ADR-0039).  
  Widened by #626, 2026-10-24 (ADR-0039 §10): each of them, `issued_by` included, may also take an artifact the source places, or the artifact the source's own structured record makes, where the passage conveys the fact; a certificate's own `issued_by` still cites the certificate. `author` and `addressee` take a person, an organization or a family, and the critic's `relation_kind_mismatch` category names them, as relations of authorship or address, with those kinds, as it names the relations of place and of agency. `carried_out_by` links an event to the organization that carried it out, such as the court of a divorce.
- `employer` (P108) links a person to an organization, orthogonal to `occupation`: what someone does (occupation, an occupation item) and whom they work for (employer, an organization item) are independent, separately-referenced claims. Date employment with start/end time.
- Organization labels keep the source's wording; normalisation is a curator edit, never an extraction guess.

## Uncertainty and time

Dates are values with precision and qualifiers; named periods may be entities. The model does not require a node for every date. Source precision is distinct from a machine's uncertainty about reading it.

- Use Wikibase time precision (year / month / day / decade / century).
- Only dates of 1 CE or later in the proleptic Gregorian calendar (Wikibase's `Q1985727`) are supported (ADR-0034). A date before the common era or in the Julian or any other calendar is never converted, guessed at or shown: the claim schema refuses one (an extraction reject whose reason begins "unsupported:"; a Julian source date is given as written, with calendar `julian`, so that it is refused rather than read as Gregorian), the GEDCOM adapter fails a file that states one in any calendar but the Gregorian or with an epoch before the common era, naming its DATE lines, the review sheet refuses a correction to one, the writer refuses a batch holding one and writes nothing, and every reader of the graph (the disagreement report, the site, the possibly-living check, the non-privileged export, which checks the whole graph at any rank first, and reconcile's roster) stops with `UnsupportedDate`, naming the item and the statement, if a curator has entered one. A GEDCOM date that names the Gregorian calendar (`@#DGREGORIAN@`, or GEDCOM 7's `GREGORIAN`), before the whole date or before one of its dates, reads as the same date written without it; a calendar inside a date phrase, or one named twice in a row, reads no date, and the adapter warns as for any date it cannot parse.
- Centuries and millennia are counted as Wikibase and Wikidata count them, from year 1: the nth century runs from year 100(n−1)+1 to year 100n, so a date at century precision stored as any year from 1801 to 1900 is the 19th century, and one stored as 1800 is the 18th. The nth millennium runs from year 1000(n−1)+1 to year 1000n (the 2nd millennium is 1001–2000).
- A claim gives a century by its first year (the 19th century as 1801), as it gives a decade by its first year (the 1890s as 1890), and the writer stores that year as it is: the wiki shows it as "19. century". A claim at century precision whose year is not the first year of its century is refused, so the 19th century given as 1800, which Wikibase counts as the 18th, is never written. Claims have no millennium precision. The static site's `format_time` and the disagreement report count as the wiki does, whichever year of a century is stored (a curator who types "19. century" into the wiki stores 1900): `format_time` shows a century-precision date stored as 1801 or 1900 as the 19th century, and the report gives it the span 1801–1900 ("Contradictions"). `format_time` names a century or a millennium with its English ordinal (the 1st, 2nd, 3rd, 11th, 21st, 101st century) and shows a date at millennium precision as its millennium, counted from year 1 as above, so one stored as 1001 or 2000 is the 2nd millennium. A precision coarser than a millennium (ten thousand years up to a billion) shows as the stored year with the span its precision allows ("1900, to within 10,000 years"), never as a narrower century.
- "The 1800s", meaning 1800–1899, is not a century in that count, and is stated as a range, earliest date 1800 and latest date 1899, never rounded to the 19th century.
- Ranges and vagueness: earliest date / latest date qualifiers. On a statement dated as a period (a marriage, a residence), each end has its own pair: see "Marriages, residences and other periods". The static site's timeline, inconsistencies and artifact pages show a stated range beside its date, each bound under its qualifier's label and at its own precision, so a range open at one end names its one bound: Rahel's death "after 1945" per the family tree shows as "1945 (earliest date: 1945)". The person and artifact pages show every qualifier of a statement so, a period's start time with its bounds and then its end time with its own, and its circa; the artifact page shows each statement that cites the artifact once, with each place its reference blocks cite it at (page, printed page, image region, fragment) and the excerpt there.
- "circa": sourcing circumstances qualifier. A compilation's statement that its text was prepared with machine assistance is another sourcing circumstance (planned: "Compound artifacts"). The static site's timeline page and feed show a statement's sourcing circumstances after the range beside each of its dates, as the person page does: Cäcilie's birth "c. 1833" per the family tree shows as "1833 (sourcing circumstances: circa)", never as an exact year. A date coarser than a year shows in the feed's display date and in the timeline page's header over it as `format_time` shows it: its decade, century or millennium, or, coarser than a millennium, its stored year with the span its precision allows ("1900, to within 10,000 years"), never as a bare stored year (a 19th century stored as 1801 is headed "19th century").
- Redundant-but-asserted values are retained. `age at death` is a string statement on the person, verbatim (for example "Alter: 73 Jahre") with its own reference, whether or not a death date is given (ADR-0040).
- **A death stated without a date is an unknown value** (ADR-0040 §2.2, §2.3).
  - A source that states a death but not its date gives a `date of death` of unknown value (Wikibase "some value"), beside any place, cause or age it gives. Examples: a GEDCOM `1 DEAT Y`; "the late" ("der selige", "покойного"), in a dated document too (ADR-0040's Q5). The one exception: a widow's or widower's marker that names the late spouse gives no death statement for them (ADR-0040 §2.5).
  - `place of burial` takes an unknown value for a burial stated without its place (ADR-0040's Q3).
  - An unknown value carries no date qualifiers, and an excerpt that states the death (its Q10).
  - A blank field, "d. ?" or "date unknown" gives no claim, never an unknown value.
  - A marker adds nothing where the same source dates the death itself.
- **"Died by" dates are derived, never stored** (ADR-0040 §2.4, its Q5). One shared derivation works them out when a view is built, as one rule: a death statement with no date is bounded by its document's own date; a stated widowhood date replaces it for the late spouse; neither is ever narrower than the date it comes from; an undated or open-ended document gives no bound.
  - A hypothetical dated postcard's "der selige Felix", whose date is "before 19 August 1938", gives Felix "died by 19 August 1938".
  - The burial register gives Cäcilie "died by 16 March 1909", at Eugen's widowhood (its Q7). The 1958 letter gives Rudolf "died by 25 December 1958", at Nina's, beside the certificate's 6 March 1941; the two differ only in resolution.
  - "Never narrower": the bound is the latest date that any non-deprecated statement of that date allows (a `point_in_time` with its `latest_date`, or every `inception` of the document), at its precision.
  - It derives bounds only from `date of death` statements (dated, bounded or unknown) and union ends, reading each document's `inception` and the survivor's `civil_status` for their dates. A burial gives no "died by".
  - A derived date is labelled as derived, stores nothing, is never written, and is never death evidence of its own.
- Ambiguous date formats (07-01-1919: 7 January or July 1?) must not be silently disambiguated. A machine's alternative readings remain proposals for review; do not present that uncertainty as precision the source itself withheld. The current claim schema represents one date value, so an unresolved choice must not be committed as though resolved.
- Named periods: statements may point to time-period items rather than dates; period items link to PeriodO ids.
- Never narrow a source's vagueness to make data "cleaner".

## Occupations, causes, counts (trial-observed vocabulary)

- **occupation** (P106 semantics) is item-valued: occupations recur across people and documents, so they reconcile like places do. The occupation item's label keeps the source's exact wording ("Hatter", "Master hatter"); cross-document variants unify through aliases and the ordinary equivalence review, never by normalizing the label.
- **cause of death** (P509 semantics) is monolingual text, kept verbatim in the source's language. Wikidata models causes as items; certificates and registers assert prose ("Wassersucht"), and the archive records exactly that.
- **sibling** (P3373) is written only when a source asserts siblinghood. It is never derived from shared parents — a source asserting two parent relations has asserted parentage, nothing more.
- **quantity** values (first use: number of children, P1971) are unitless numbers for source-asserted counts. A count is a claim like any other: competing counts coexist, and corrections in the review CSV take a plain number. `age at death` stays a verbatim string qualifier (above) — it records wording, not arithmetic. (Amended by ADR-0040, 2026-10-24, its Q1: a verbatim string statement on the person, not a qualifier.)
- **place of burial** (P119) is an ordinary place-valued property; burial places join the place hierarchy pass (ADR-0009) like any other place.  
  Amended by ADR-0040, 2026-10-24, its Q3:
  - Its subject is a person (`human` or `unclassified_entity`), as for every death property.
  - Its `point_in_time` is the burial's own date as the source gives it ("Beerdigt: 20. März 1909"), never the document's date. No `date of death` and no "died by" date is derived from a burial (ADR-0040 §2.4).
  - A burial stated without its place gives a `place of burial` of unknown value, dated where dated.

## Places

- Reconcile to GeoNames and World Historical Gazetteer where possible; store external ids and coordinate location.
- Historical places that no longer exist are ordinary place items with their own time bounds.
- **Containment between places is a source's claim** (ADR-0038). `A part of B` is stated in the source that says so, with its locator, at normal rank beside any contrary source's claim, and a machine-written one also cites its run. No source, no containment: nothing writes a `part_of` no source states, and process provenance alone never backs one. `location`, which places an organisation or an event, follows the same rule. The 1905 marriage certificate puts Fläckfeld in Kreis Mockburg and the 1984 family tree in Kreis Peiltal: both claims stand, each with its source. No model answers whether one place lies within another; the only question a model may be asked is which existing place a source's container name means (ADR-0038 §3).
- **A containment carries the time its source gives, and nothing else**, dated as a residence is ("Marriages, residences and other periods"): `start_time` and `end_time` where the source dates its start or end, each with its own range (a start from its `earliest date` to its `latest start date`, an end from its `earliest end date` to its `latest date`); `point_in_time` where the source presents it as holding at a date, bounded by `earliest date` and `latest date` where the source gives a range; circa as `sourcing circumstances`. A source that states no time gives a containment with no time qualifier: the document's own date is never written as the containment's point in time (rule 5). Views read an undated claim as of its source, labelled by that source ("Fläckfeld: in Kreis Mockburg per the 1905 marriage certificate; in Kreis Peiltal per the 1984 family tree").
- **The place hierarchy asks identity alone** (ADR-0009, ADR-0038 §3 and §8.5, #201). A place's mention record states the chain of containers its source puts it in, and each link of the chain is a link the source states. Where a link's container names more than one existing place, or no claim of the document gives the link, a model is asked which existing place the container means, among the places that bear its name; it answers with one of them, or none. The link is then written `part of` the place named, at normal rank, `stated in` the document's artifact and `inferred from` the pass's run item, with the time the document's claim gives and none where the record alone states the link. The `stated in` block carries the container's evidence, the source's words that state the link, as its `transcription excerpt`, with the `page number` (and `printed page number`) of the transcription page the evidence's first line lies on, where the transcription has pages; a container with no evidence gives the artifact alone. An equal statement already citing the artifact keeps its blocks as they are: for a link a claim of the document also gives, its block records the link and nothing is added; for one the record alone states, a block without the excerpt gains the excerpt's block beside it, never a duplicate statement (ADR-0038 §8.5). A link that would close a cycle, at any time, is refused. A scratch run does this unattended in its `places` stage; `yizkr reconcile-places` asks the same for a curator, who approves the answers it writes. A GeoNames-imported edge is stated in the GeoNames dataset item (ADR-0038 §6).
- The inconsistency report suppresses value pairs connected by a path of `location` and `part_of` claims, differences of resolution rather than contradictions, and follows only a claim that a source states and a curator has not deprecated, at any time it carries ("Contradictions").
- The GEDCOM adapter gives each link of a PLAC's chain of components as a `part_of` claim of the export, from the place to its nearest jurisdiction and from each jurisdiction to the next, each jurisdiction a place of its own, with no time, since a PLAC states none: "Brunnenring 35, Flörburg, Hesse, Germany" gives Brunnenring 35 in Flörburg, Flörburg in Hesse and Hesse in Germany (ADR-0035 §6).
- Extraction gives a place's `part_of` only where the source states it (in the place's mention, "Fläckfeld, Kreis Mockburg"; in the fields a form gives that place; or as a link of a chain of containers), never from what is known of the place or from another place's container, with the time the source gives it for the containment and none where it gives none. Neither the document's own date nor the date of an event the source places there is that time: a birth "in 1836 at Flörburg, Kreis Peiltal" gives Flörburg's `part_of` no time. The extraction critic flags a `part_of` claim whose citation, read where it stands in the numbered transcription, does not convey the containment or a time it carries (`unsupported_containment`; ADR-0003's test, ADR-0023, amended by #607).

## Artifact coverage — cross-domain relations (planned)

Artifacts do not only assert claims about people and events; they also _cover_ regions of other domains: a map covers a geographic extent, a census page covers a district on a date, a letter spans two places. These cross-domain coverage relations (cf. Dublin Core "coverage") are ordinary statements on the artifact item, and the reference requirement (ADR-0003) applies unchanged: what an artifact shows about itself is referenced `stated in → the artifact itself` (the registrar convention above); coverage computed by a tool (e.g. georeferencing software) adds an `inferred from extraction run` reference like any machine write.

Planned first instance — **georeferenced map artifacts**:

- a `map` subclass of artifact;
- two globe-coordinate properties on the map item, `bounding box north-west corner` and `bounding box south-east corner` (an axis-aligned extent; Wikidata's extremum-point properties P1332–P1335 are the nearest semantic precedent), so interactive maps (R6) can draw the artifact's outline in place and SPARQL can answer "which artifacts cover this place?";
- W2 upgrade path: IIIF Georeference annotations (Allmaps-style ground control points) refine the flat bounding box exactly as IIIF canvas+xywh URIs refine percentage regions (ADR-0004) — the corner properties then remain as a cheap derived summary for query and display.

Other domains follow the same shape rather than inventing new machinery: temporal coverage (the period a map _depicts_, distinct from when it was made) reuses `time period` / date properties, and subject coverage uses `main subject`; who or what an image shows, as its own content states it, is `shows`; `depicts` is the faces flow's confirmed depiction (ADR-0005; ADR-0039 §2.2). Prefer an existing Wikidata-mirrored property, keep values structured (never strings), and reference the artifact itself or the producing run.  
Widened by #626, 2026-10-24: `shows` may also come from a source that places the image, where its passage conveys it (ADR-0039 §10.4).

## Compound artifacts (see ADR-0008)

**Current limitation:** excerpts, extraction context and registration take PDF and PPTX source parts and placements from the [shared source consumers](ARCHITECTURE.md#shared-source-consumers), independently of reading strategy. A page read by vision that holds an inner source or annotation cannot separate their assertions from the compilation's, so its claims are unsupported and extraction stays incomplete rather than attributing them to either. Every original image, including full-page scans and picture backgrounds, is an independent source. A proven sole-image page reads through that image and avoids duplicate parent claims; generated page renders are representations. Configured model-input exclusions apply before PDF vision dispatch: an excluded image or uninspectable content refuses the affected route, and whole-document vision receives checked page pixels in a rebuilt PDF. [The reading guide](LLM_CACHE.md#pdf-model-input-exclusions) explains the boundary and reuse checks. The container's own file is still registered as held, so filtering model inputs or derived images is not redaction of that file.

**Documentation TODO — [#735](https://github.com/WillHirsch/yizkr/issues/735):** consolidate this section's remaining caption/preparation amendment prose into verified current behavior; remove this marker when that cleanup is complete. The current document-subject rules are summarized above, and the approved contract governs attribution and disclosure.

- A container artifact (first case: `presentation`, a slide deck) keeps the standard registrar shape: its slides ARE page fragments (`part_of` + `page number` qualifier), and claim locators reuse `page_number` as the slide number.
- Each eligible original image with verified owner bytes becomes its own artifact item, regardless of size, coverage or placement. Picture backgrounds inherit through slide/layout/master/theme definitions and retain each actual slide occurrence. A `part_of` statement carries a page/slide qualifier only for a verified paint; an unplaced source retains original-part provenance without an invented position. Native vector shapes remain container content. Preparation records owner bindings in `container-inventory.json`; registration preserves them. Repeated placements and background/shape uses share the established image owner. Unsupported or ambiguous preparation stays explicit and cannot invent a readable source.
- Every statement a container contributes to a derived item is referenced `stated in → that container` — a compound artifact asserts its own composition, the same convention as fragments and registrar statements above.
- Derived items follow artifact identity: they carry `media SHA-1`, so one image embedded in several containers is **one** item, `part_of` each of them (each statement slide-qualified and stated in its own container). A statement that several containers make alike (`instance of`, `media file`, `media SHA-1`) is one statement citing each of them; a later container's name for the item is an alias, unless another item already has that label (ADR-0008 as amended by #50).
- PPTX unpacking is deterministic: slide text and speaker notes come from XML, with separate source-part support. Eligible original images are read independently; readings that contain document content become excerpts whose claims cite the image. Empty or non-document readings remain recorded without an excerpt. Whole-slide visual reading follows the same ownership and exclusion principles as PDF reading, but its implementation is pending [#747](https://github.com/WillHirsch/yizkr/issues/747).
- **A compilation's original excerpts are artifacts of their own** (ADR-0008 as amended by #289, #176 and #397). A compilation sets text of its own (a typed translation, commentary) beside images of excerpts from the originals it draws on: two witnesses of one text, which may disagree. An independent image that a PDF places within one of its pages is a derived item like a deck's: keyed by its SHA-1, `part_of` the PDF once per page it is on (page-number qualified), labelled "<title> — page <n>, image <k>" for its first place, and an `instance of` photograph. An image covering most of its page is a page representation and is not read on its own, unless a verified existing owner binding makes it an independent source; the inventory keeps it as a source part either way. A PDF with a text layer, or with an independent image source, is read page by page, and each independent image it places, on a text-layer page or a vision page, has a transcription of its own (ADR-0008 as amended by #176), which is extracted as a document of its own, an excerpt, whose claims cite the image; the write registers the image's item, after the PDF, before any claim that cites it (ADR-0008 as amended by #397). The same image in several PDFs is one item and one excerpt; an image whose bytes a document of the corpus has is that document. An image whose reading's record calls every page blank or not a document page (a photograph with no writing, a colour chart) is registered but is no excerpt; an illegible one is an excerpt, so that a reader sees it was there. An excerpt's language and class are its reading's record's (ADR-0037). An independent image on a page read by vision is still read on its own as an excerpt, but the page-wide reading cannot separate its assertions from the compilation's, so that page's own claims are unsupported (see the current limitation above); the same holds for a vision page that shows an annotation.
- A claim cites the witness that asserts it. A claim read from the compilation's own text cites the compilation, with its page as the locator; a claim read from an excerpt cites the excerpt, with no page number and optionally a region of the image. Each transcription excerpt is tagged with the language it is written in, so a retyped transcription in the compilation takes the original's language. Each witness has its own transcription and its own batch, and an extractor cites the document it read, so neither witness's claims can cite the other.
- **A container's words about an artifact it places are its `caption`** (ADR-0039). A caption, a heading over an image or a sentence of commentary that speaks of it is one verbatim `caption` statement (monolingual text, in the container's language) on that artifact's item, `stated in` the container with the page or slide it stands on; nothing in it is normalised, cut or translated. What the artifact is (who made it, for whom, when, where, what it is about, whom it shows) stays its own claims, which cite it: the booklet's "Wastl to Klara, July 1939." is the booklet's caption on the letter's image, and the letter's "28. Juli 1939" is the image's own `inception`. Nothing crosses: the excerpt's extraction never reads a caption, and the pipeline never turns one into a structured statement. From the keeper run on, a curator may promote a caption's fact, `stated in` the container with the caption as its excerpt, or combine two sources' values as a new statement with both references and the qualifier `determination_method` → `combined_from_sources` (ADR-0039 §4).  
  Widened by #626, 2026-10-24 (ADR-0039 §10): the caption stays one verbatim statement, and beside it the container states the seven document-subject properties of the artifact where its passage, read where it stands, conveys them, cited to the container with the page and the passage as its excerpt: the caption gives the letter's image `author` → Wastl and `addressee` → Klara, but no `inception` from its "July 1939", which it ties to no event; the booklet's translation of the dateline gives `inception` → 28 July 1939, `location_of_creation` → Brunnenring 35 and `addressee` → Pünktchen, each `machine_assisted`, and no caption. A line about the reproduction (who scanned it, when) gives no such claim. A curator may still write, from the keeper run on, a fact the extraction missed.
- **The static site shows what sources say about an artifact** (ADR-0039 §7). An artifact's page has a section "What sources say about this artifact": its captions first, each with the container that gives it and the page and printed page it stands on ("per _Our Family from Germany_, page 6 (printed 4)"), then its own document-subject statements, each property's values listed together, each with its source ("per this artifact" where the artifact states it of itself), none preferred, in the order of their text; a date at its stated precision with its qualifiers (its range, circa), an item by its label, a person the roster lists linked to their page and, when possibly living, badged as on the index. A person's page has a section "Named in artifacts": each document-subject statement whose value is the person ("shown in" the portrait, "addressee of" the letter), with its sources. A caption names no one, so it is never listed there.  
  Widened by #626, 2026-10-24 (ADR-0039 §10.2): the section also lists what other sources state of the artifact, each value with its source, page and printed page, every value of one property together, none first; "Named in artifacts" labels values the same way; and an un-held media item's page shows its `inception`.
- **Machine-assisted preparation is a sourcing circumstance.** When a compilation states that its text was prepared with machine assistance (that its translations are machine translations, say), each claim read from that text carries `sourcing_circumstances` → `machine_assisted`: the claims read from the passages the statement names, or from all of its own text when it names no part. The manifest's one sourcing circumstances value, `circa`, says that a value is approximate and does not fit, so `machine_assisted` (label "machine-assisted") joins the manifest with the extraction change that sets it (planned). The marker records what the source says of its own making: it is never inferred from how a text reads, never set on an excerpt's claims, and never a rank. The pipeline's own machine work stays process provenance (ADR-0003, ADR-0023). Like circa, it makes the compilation's claim a statement of its own beside the same value from a source without it.  
  Built by #666, 2026-10-24 (ADR-0008, the #666 amendment): the manifest holds `machine_assisted`, which no prompt offers; the entity manifest reads the document's statement once, quoted verbatim with the lines it covers ("all", or the passages it names), or the passage a curator points to (`preparation.pointer.txt`), and the pipeline marks every claim whose excerpt stands within those lines, dropping any marker a chunk gave. A claim it cannot place within or outside them is not marked, and the batch says so. Each marked statement cites the statement too, in a reference block of its own: `stated in` the same artifact, with the statement's page and the statement as its transcription excerpt, beside the claim's own source block (rule 1: the marker's evidence is referenced).

## Faces and depiction (see ADR-0005)

- A face identification links the photograph item to a person with `depicts` and the qualifier `relative position within image = "x%,y%,w%,h%"`. Detection or manual marking creates a region; matching proposes identity. Each association requires affirmative human confirmation. Several displayed associations may be confirmed together, but generic document/run acceptance must not confirm faces.
- Current commands are `yizkr ingest detect-faces`, `enroll-face` and `match-faces` (`pipeline/faces.py`). They produce proposals for the shared review flow. Enrollment supplies a gallery example, not confirmation of later matches.
- The current CSV implementation requires a per-row approval and refuses bulk acceptance for `depicts`. `apply_review` records `row_approval`, binding the claim and the manifest records of its local references. The writer validates it before instance access. This digest is batch review state, not an authenticated curator signature or a durable graph-revision binding; the [ingestion contract](INGESTION_CONTRACT.md) defines the target boundary, implemented through #130 and #142.
- The statement references the photograph and region plus the detection run for a machine proposal. The reviewed batch and edit history record the confirmation action. Source/run references alone are not a complete account of the human decision. Rebuild runs omit `depicts` entirely.
- **Associated media vs. depiction (ADR-0021).** `image` links a person to a medium a source associates with them, such as a portrait or obituary scan. The GEDCOM adapter emits it for OBJE records as un-held media items of kind `artifact`, with neither `media file` nor `media SHA-1`. It does not fetch the referenced bytes. The `image` claim is undated; an object's own DATE becomes its media item's `inception`, with the source's precision and bounds. Acquiring media is a separate authorized step and uses content-keyed artifact registration.
- **Source wording vs. confirmation (ADR-0039).** `shows` records whom a source says an image shows, from the image's inscription or a container's supporting passage. `caption` records a container's verbatim words about the image. Neither is a confirmed region-to-person association or maps to `depicts`. Any use of those words to propose a face match still needs the confirmation gate.
- IIIF annotations, photo-service integration and XMP/MWG export are optional follow-ups (ADR-0004, ADR-0005), not implemented substitutes for this gate.

## Names (see ADR-0011)

Names are modelled in **two layers**:

- **Aliases** (the entity's label + `altLabel`s) remain the flat, append-only, _unreferenced_ index that reconciliation blocks on and label lookup uses. Every name form a document uses goes here.
- **Typed name statements** are the source-first record, used when a source states a name's _kind_. Each is an ordinary referenced claim (monolingual text, source's wording kept verbatim) and may be dated with `start time` / `point in time` (a formal change is a dated event):
  - `birth name` (P1477) — name/maiden name given at birth;
  - `married name` (P2562) — family name taken on marriage;
  - `nickname` (P1449) — a name the source marks as what the person is called, by anyone ("Peppi", "Gustl"), or an "aka"; what one person calls another, or a name that names the person through a relation, is `referred_to_as` alone (below);
  - `official name` (P1448) — a formally adopted or legally changed name.
- **A name form of no stated type** (ADR-0011, amended by #435): where a source gives a person a name form without stating its type, beside the label's, it becomes a referenced `name` (P2561) statement, verbatim, as well as an alias. It is never made for the label's own form or for a form the source types, both compared in NFC with whitespace collapsed and lower-cased (a sharp s kept apart from "ss"), and validation refuses one that restates its subject's label or whose subject is no person (an unclassified entity takes one). In a document it is only for a distinct name whose kind the source leaves open, never a shortening, an initial, a spelling variant, a part of the label or an unmarked nickname use. A bracket holding a cue or a note ("(geb. Laudler)") gives its text verbatim: code never types a name from its wording. A curator who identifies the type later adds the typed statement citing the same source, beside it, and may lower its rank.
- So each kind of name form goes here: the label's own form, to the label alone; a form the source types, to an alias and its typed statement; a further form of no stated type, to an alias and a `name` statement; and an appellation, any other form a source uses to name or address the person (a kinship term with a name or alone, a pet name, a courtesy name), to an alias and a `referred_to_as` statement (below; ADR-0018 as amended by #499).
- Typing adds structure where a source marks it; it never narrows or infers (a maiden name is recorded only when the source says so, never derived from gender + marriage).
- The GEDCOM adapter emits these from NAME TYPE, the NICK and `_MARNM` tags, and the inline convention that a quoted part is a nickname ("Cäcilie 'Cilli' Tarle"). A bracketed part ("Ida (Peppi) Sörne") may hold a nickname, a maiden name or a note, so it is an alias and an unsplit form of the mention record, typed as nothing and counted, and a `name` statement, and the label leaves it out; a further NAME with no TYPE, or a TYPE the adapter does not recognise, is a `name` statement too, unless it is the label's form; no `name` statement comes of a form the person's record types (a recognised TYPE or a `_MARNM`, whether or not a typed claim is made of it), of the display form of a NAME that held a placeholder anywhere, or of a bracket that held one (a complete bracket of such a NAME still gives one); a lettered stand-in ("N.N.") holds letters and stays a `name`; a NAME without slashes, whose parts no GIVN or SURN gives, is an unsplit form too, and its TYPE gives no claim, and one with only a GIVN or only a SURN keeps its whole value as an unsplit form beside that part. A `_MARNM` gives a married-name claim only where its slashes hold a surname; otherwise it is an unsplit form too (ADR-0035 §6). A GIVN's quotes and brackets read as the value's do: a quoted part is a nickname, a bracketed part an alias and an unsplit form. A word that holds no letter or digit ("?", "\_", "()") is a placeholder, in a value, a bracket, a quote, a part or a NICK: it names nothing, so it is counted, not placed ("Eugen /?/" is labelled "Eugen"), and a typed name that held one anywhere but in a NICK, a stray bracket included, gives no typed claim; a single dash or "&" between two words of one field is a connector, kept, and one against a slash, a bracket or a quote, a "+" or a run ("--") is a placeholder. As many SPFX slots as SURN slots pair by position, empty slots included. German low quotes and guillemets mark a nickname as other quotes do. Where no NAME gives a name, the label falls back, marks and all, to brackets that hold a word ("(Peppi)"), then a GIVN's quotes or brackets, then a NICK, then a `_MARNM`; a person with none of these words is skipped and counted, as one with an empty NAME is. The adapter's texts are in the export's language (HEAD.LANG, mapped to BCP 47), or undetermined (`und`) where it states none. Typed names also feed reconciliation: a married name matching another's birth name (a marriage name change) is strong identity evidence.

**Name normalization (ADR-0022).** Three axes are kept distinct: _composition_ (which token is the fixed part vs. an alternating one — the `/` in "Hildegard Laudler/Löbig" prescribes it, so those surnames are alternative family names for one person), _kind_ (given vs. family — undecidable without name-order convention, so **never asserted** and never a stored property), and _type_ (birth/married/nickname/official — recorded only where a source marks it, the marker possibly contextual). The LLM is the primary normalizer: its prompt carries these standards (compose no permutations, keep a clean label, strip embedded annotations, type only what is marked). A thin deterministic validator (`pipeline/names.py`) is the shared safety net over both the LLM and GEDCOM paths: it reads an alias through the entity's mention record, never its token shapes (ADR-0035 §8). A person's alias that gives no name part is dropped, as is one whose parts the label already gives ("Löbig, Ida" beside "Ida Löbig"); one that adds a part is kept ("Wastl"), as is one that spells a part otherwise than the label ("Gustav Lobig" beside "Gustav Löbig"), and so is the first that alone holds a title or suffix the record gives ("Frau Löbig" beside "Ida Löbig", her record titling her Frau). An alias the document gives as an appellation (the value of a `referred_to_as` claim of the same document about the entity) is kept when it holds a word that is no name part ("Tante Rahel" beside "Rahel Löbig", "Omama"); one made only of name parts is judged as any other, so a reordering stays dropped. Where a person's label is one of those appellations and its record stands with the status `name`, the label becomes the name the record gives. Every form, the label and each alias, competes: one made only of name parts as itself, any other with its longest run of name-part words, never joined across a word that is none ("Rahel Löbig" of "Frau Rahel Löbig geb. Tarle"). One that is no appellation wins, then the one of most words, a whole form before a run, most letters, least punctuation (so "Rahel Löbig" before "Löbig, Rahel"); with no form holding a name word, the label stays. The appellation stays an alias, every local ref takes the new label, a `name` claim restating the model's label stays a reject, and one restating the new label is dropped and counted (`appellation_label_names`). A `referred_to_as` the manifest turn did not list joins the person's aliases. This runs where the batch is assembled, once the chunks' claims exist, and fires on marked appellations only, never on a word the record merely leaves out. The GEDCOM adapter cleans by the record it fills, as extraction does. A place's or an organisation's alias that gives no part (a deictic or generic reference) is dropped, and a short form kept. An entity without a record keeps its aliases, blanks and duplicates aside. It never splits a name, so compound/particle surnames stay whole (`Faxridge-van 't Nijks`), and asserts no kind. Composition and short-form display are the frontend's to _derive_, never stored.

**Mention records (ADR-0035 §2).** Extraction's entity manifest may give each person, place, organisation and family a `structure`, what its names are made of, read from its label and aliases as the document writes them, by the document's own conventions and never by a rule about a language:

- **a person:** a status (`name`, `role`, `kinship`, `courtesy`, `placeholder` or `description`; only a `name` keys); given names as written, each with the standard form a diminutive or abbreviation stands for where the document supports one, and marked when it is an initial; surnames typed `birth`, `married` or `other`, with their particles; patronymics, a name part of their own (the 1941 certificate's _Лёбиг Рудольф Феликсович_ gives the given name Рудольф, the surname Лёбиг and the patronymic Феликсович); nicknames, the names the person is called by anyone, each also an alias (a pet name among them also a `referred_to_as` appellation; a form through a relation, such as "Tante Rahel" or "Nana Maisie", is never a record part, ADR-0018); titles, honorifics and ranks and never a kinship word, and suffixes, which never key; and `unsplit` forms whose given name and surname the source does not tell apart;
- **a place:** a status (`toponym`, `deictic`, `generic`, or `adjective` for a country a source gives only by an adjective of nationality, which keys nothing); its names, each with its toponym and generic head where they can be told apart; an address, with its street and number; and the containers the source puts it in, nearest first, whatever order the source writes them in (`within`: _Snylsjum, gemeente Drakeradiel, Fryslân, Nederlân_ is Snylsjum within the other three; a form whose fields run oblast, district, village puts Koshnovka within Kaldovsky District, then Chadsk Oblast). Each container carries its evidence, a verbatim excerpt of the transcription that states the containment: the mention in running text, the field's line on a form (ADR-0035, amended by #569). The evidence is a citation, a located passage: read where it stands, it conveys the containment, so a container's name alone in the district field of a form about the place is evidence enough, while a name in a list of towns is not (ADR-0003, amended by #607; the critic may flag one that does not, `evidence_does_not_state`). Each container in `within` is a place entity of the manifest too, with its own record, and so in turn is each of its own containers (_Fläckfeld, Kreis Mockburg, Hesse_ gives three place entities; ADR-0035, amended by #572);
- **an organisation:** its proper names, the words naming its kind, and its places (_Калдовское районное бюро ЗАГС_ has a kind and a place, and no proper name);
- **a family:** its surnames.

**A record is never written to the wiki**: it is the pipeline's reading of a name, not something a source asserts, so ADR-0022's Ruling 1 holds for the graph. Records live in the batch view and the LLM cache, as local-only data. A record may divide and label a name, never add to it: every part must occur in the label or an alias, folded, as whole words (a standard form, an organisation's places and a place's containers aside); a place's written name that is its label and then one of its own containers stands, counted as `label and container`, while that container stands (ADR-0035 §5). A place's container stands on its evidence instead, and one that fails (`no-evidence`, `evidence-not-in-source`, `evidence-does-not-name`), or that cannot become a container at all (`malformed`: its evidence a list, a key a container has not, no name), is dropped alone, its record standing; each drop is counted by reason, apart from the records set aside (ADR-0035 §5, amended by #607). An optional field the model writes as an empty string is read as absent, and a name part that is empty, or whose written form is, is dropped and counted (`dropped`); an entry of a list of strings written as an object holding only its `written` text (a family's surname also its `type`) is read as that text and counted (`read as text`); the record stands if what is left can. A record that fails that, or that does not parse, is set aside and counted, and the entity keeps its label, aliases and kind. The GEDCOM adapter fills each person's record from the NAME's value and its GIVN, SURN, SPFX, NPFX, NSFX, NICK and `_MARNM` (ADR-0035 §6): a part the value does not restate reaches its field, and the name it completes (the name the parts give, or an NPFX or NSFX beside the value's name: "Dr. Eugen Löbig") becomes an alias, counted; in a NAME with no value, a prefix or suffix with no given name or surname beside it is counted instead, so none is dropped silently. A NICK and a `_MARNM` are aliases too. A place's record takes its PLAC's first component as its name and the rest as the places it is within, each with the PLAC's value as its evidence. Each of those jurisdictions is a place of its own too, one per distinct tail of components in the export, and each place carries its own name as its label or an alias; each link of the chain is an undated `part_of` claim cited by the PLAC's line. A component without a word ('?') is left out and counted. A placeholder word ('unbekannt', 'unknown', 'onbekend'; the list in `pipeline/gedcom_placeholders.yaml`, which is data and may be extended) is record-only, by the owner's decision: it stays in the place's `within` as written, with no place, no `part_of` to or from it and none across it, so that two unknowns are never one place; it is counted (ADR-0035 §6). What a marker in a name asserts (a widow's marker, "the late", a patronymic's father, a married-name marker) is a claim: a `civil_status`, a death, a `father`, a `married_name`.

The entity-manifest prompt asks for each record, and for each label's status, by the structure of what it reads (a surname-first register, capitals, a maiden-name or married-name marker, a courtesy title, a place's generic head, an institution's kind), with examples from the universe's sources in German, English, Russian and Frisian, and lists no marker words. A person the document does not name is labelled with the document's own words for them (the postcard's _Dein Vater_, status `kinship`). Any manifest entity or claim may carry a **judgement note** (ADR-0035 §4): a category (`kind`, `relation`, `date_reading`, `identity` or `other`) and one sentence in English, only where the extractor made a call a careful reader could make differently. `coverage.json` counts the records given (and by status, and the `unsplit` forms they hold), recordless and set aside (the records, and the reasons by category), the labels the appellation rule replaced with a name (`appellation_labels`), the `name` claims dropped for restating one (`appellation_label_names`), the record name parts that are appellations (`appellation_parts`), and the notes by category.

**Appellations are aliases and sourced statements** (ADR-0018, amended by #499). Every form a source uses to name or address a person is an alias, with no structural distinction: a name form, a kinship term with a name ("Tante Rahel"), a kinship term alone ("Omama"), a pet name ("Pünktchen") and a courtesy name ("Nana Maisie"); that the person was known by it, to at least someone, is what the alias keeps. Each form that is no plain name form (a name, or a spelling, a shortening, a diminutive or an initial of one) is also one `referred_to_as` (P1810) statement on the referent: verbatim, referenced to the artifact with its locator, and qualified by `perspective` (the person/family ego) when the source gives an ego that is a modelled entity, unqualified otherwise. The alias is the lookup; the statement is the evidence. A literal kinship term also gives a `relative` + `kinship_type` claim with the ego as object (§Kinship); a spousal term ("my husband") gives a marriage (ADR-0036). A description that is no form of address ("the deceased", "the informant", "my husband", "our great grandmother", a role or form-field label) is never an alias. The label stays the display name: a name form wherever the document names the person, and the document's own words only for a person it never names. Where a person's label is one of the document's appellations and their record names them, every form competes for the label: one made only of name parts as itself, any other with its longest run of name-part words (never joined across a word such as "geb."), so "Omama" beside "Oma Hildegard" becomes "Hildegard". For identity, a recordless person never keys on a form its document gives as an appellation, as label or alias; a person with a record keys on its name parts; and a pet name the person is called by anyone stays a record nickname and keys as one (ADR-0035 §7). Reconcile's blocking against the graph (ADR-0007) keys the same way on both sides: a person's label or alias that its batch, or the item's own `referred_to_as` statements, give as an appellation keys nothing, a typed or record nickname keys, and the adjudicator reads an appellation as what the entity is called ("called: Oma"), not as an alias. Places, organisations and families, never persons, key on marked forms as on any other name; persons and the kinds that may be persons (an unclassified entity, a ref with no kind) never do. Appellations are multi-valued and coexist (ADR-0002): many people may call one person many things. Because each appellation is a statement whose _subject_ is the referent and whose ego (the `relative` object or the `perspective` qualifier) is the other party, reciprocal naming (a grandmother "Oma" to a grandchild who is "Bubele" to her) is just two independent statements — no dyad object, and the kinship inverse is derived, not stored. With the ego anchored, a later bare reference resolves: compositional terms by kinship derivation, idiosyncratic ones via the appellation table. Appellations of possibly-living people ride the possibly-living exclusion (ADR-0020).

## Kinship (see ADR-0014)

Kinship is modelled in **three layers**, so the graph stays a thin primitive network and the _same_ term set describes any pair:

- **Primitive edges (stored, source-attributed):** `father` (P22), `mother` (P25), `sibling` (P3373), `child` (P40). `sex_or_gender` (P21; `male`/`female`) is stored alongside — the calculus needs it to gender terms. A spouse is no stored edge (ADR-0036): a marriage is an entity whose couple take part in it with the role `spouse`, and the spouse link is derived from it by a query; the `spouse` property (P26) is retired. A spousal term ("my husband") gives a marriage, not a kinship class. `sibling` stays asserted-not- derived (a source may assert siblinghood directly) yet is _also_ derivable from shared parents; both coexist.
- **A derivation calculus (query/frontend layer — NOT vocabulary):** second-order relations (grandparent, aunt/uncle, cousin, in-law) are property PATHS over the primitives, mapped to a shared gendered term set. See `src/yizkr/queries/kinship.rq`; the full pairwise calculus with degrees (great-, once-removed, half-) is a frontend build over the same primitives. Never store a derivable relation.
- **A source-asserted compound fallback:** `relative` (P1038) with a verbatim `kinship_type` qualifier holds a compound relation a source states but that primitives cannot yet capture unambiguously ("maternal aunt", connecting parent unknown; blood vs marriage undetermined — never narrowed). One property, not one per relation; the calculus and this qualifier share the same term set, so asserted and derived relationships describe uniformly and coexist (a match corroborates, a mismatch is an ordinary inconsistency).
- **A kinship class beside the term (ADR-0035 §3.3).** A `relative` claim keeps its verbatim `kinship_type` and gains a controlled `kinship_class`: `kin_parent`, `kin_child`, `kin_sibling`, `kin_grandparent`, `kin_grandchild`, `kin_aunt_or_uncle`, `kin_niece_or_nephew`, `kin_cousin`, `kin_parent_in_law`, `kin_child_in_law`, `kin_sibling_in_law`, or `kin_relative` where the term's class is unclear. Three more qualifiers hold only what the term states, never a guess: `side` (`paternal` or `maternal`), `degree` (how many "great-"s, or a cousin's number) and `removes` (a cousin's removes). The 1958 letter's _дядя по отцу_, "uncle on the father's side", is `kin_aunt_or_uncle` of degree 0 (a term other than a cousin's with no "great-" has degree 0) on the `paternal` side; its _двоюродная сестра_, "first cousin", is `kin_cousin` of degree 1; the 1952 letter's _oerbeppe_, "great-grandmother", is `kin_grandparent` of degree 1. A literal term that reduces to a primitive stays one: _Dein Vater_ is `father`.
- **Civil status is a person's own state, not a relation.** A source's stated civil status (`unmarried`, `married`, `widowed`, `divorced`) is a `civil_status` claim, dated as the source dates it. It names no partner and makes no marriage; a marriage comes only where a source names the partner (ADR-0036).
- **Participant roles.** A `participant` qualified by `object_has_role` (P3831) says how someone took part in an event: the `principal` (the one born, who died, or to whom it happened), a `parent`, the `informant` who reported it, a `witness` or the `officiant`; in a partnership or marriage, a `partner` or a `spouse`. One claim may carry several roles, but a death's principal is never also its informant. The GEDCOM adapter makes each death event it makes with the person as its `principal`, and each union's couple its `spouse`s or `partner`s.
- **Amended by ADR-0040, 2026-10-24**, carried out by its build:
  - Births and deaths have no event and no roles. The one born or who died is the subject of their own statements, and a birth's parents are `father` and `mother`, each cited.
  - `parent` and `informant` are retired as roles (ADR-0040's Q6), and "a death's principal is never also its informant" goes.
  - A person who only certifies, registers, officiates, examines, reports or witnesses is left out, unless the same record gives them another role (kin of someone it is about, or a party to it). A wedding's registrar and non-kin witnesses are left out; a kin witness or officiant stays, with that role.
  - Persons only, as decided; its scope over a record's apparatus (certificates, registers, forms) is lean-only, so organizations stay `issued_by` or `carried_out_by`, and a doctor whom a letter names stays. Also lean-only: a person given only by the role in which they report or certify, with no name, is not made. Its case, "Informant: husband", records nothing by the owner's decision (2026-10-24).
  - The GEDCOM adapter makes no death event.
  - Roles stay for the other events and for unions.
- **A parent's kind** (ADR-0040 §4).
  - `father`, `mother` and `child` take a `parentage` qualifier: `parentage_birth`, `parentage_adoptive` or `parentage_foster`.
  - It is set only where the source's words or tags state the kind ("Adoptivvater", "leiblicher Vater", "foster mother", a PEDI tag), never inferred. A register's parents carry none.
  - The word stays verbatim in `kinship_type`, which `father`, `mother`, `child` and `sibling` may now carry.
  - An adoption's date is a `start_time` on each adoptive parent statement, and a fostering's a `start_time` and an `end_time`. The court is the order's `issued_by`.
  - The kinship query labels adoptive paths and derives nothing from a foster link.
  - The GEDCOM `PEDI`, `_FREL`, `_MREL` and `ADOP` tags are counted, not mapped, until a source carries them.
- **Step and half terms** (ADR-0040 §4). A step term is `relative` with `kinship_class` `kin_step_parent`, `kin_step_child` or `kin_step_sibling` ("mein Stiefvater", hypothetical). A half term stays `sibling`, with the word ("Halbbruder") in `kinship_type`.

## Residence and co-residence (see ADR-0014)

`residence` (P551) is directed **person → place** and multi-valued: each co-resident is the subject of their own referenced statement pointing at the same place item, with its own date qualifiers. The place is never the subject; there is no household statement enumerating occupants.

- **Attribution on extraction.** An address stated on a form is asserted for the person the field names (e.g. the informant on a birth certificate), not for everyone the document mentions. One person's stated address is never propagated onto others as their residence; a dependent's residence inferred from a relative's address (a newborn at the parents' address) is recorded only at lowered confidence.
- **Co-residence is derived, never stored.** "Lived with" is a PATH — two people with overlapping residences at the same place over overlapping time — computed in the query/frontend layer, exactly like kinship. No `co-resides-with` edge. (Asymmetric sheltering — "gave refuge to" — is the separate, non-derivable case ADR-0014 tracks.)

## Marriages, residences and other periods

ADR-0036 makes a marriage an entity bounded by events, and retires the `spouse` statement below; its vocabulary is in the manifest ("Core classes"). The extraction prompts ask for marriages so: the couple take part in the marriage (or partnership) with the role `spouse` (or `partner`), the union is `started_by` its wedding and `ended_by` a divorce, an annulment, a partner's death, or an event of unstated kind where the source does not say how it ended, and each of those events carries its own date and place. A marriage whose start the source dates or places, at any precision, gets its wedding, as a stated divorce gets its divorce; a marriage the source only names, a partnership, and an observation (a directory or census that lists the couple as married, with no start) get no wedding (#656). In the 1984 tree, "= (1942) Florence Faxridge" gives a marriage and its 1942 wedding, and the undated "= Hildegard" gives the marriage alone. The run report counts each extraction's marriages by their weddings: started by a dated wedding, by an undated one, or by none. Until the rest of the pipeline moves to marriages, the readers of spouse statements (among them the disagreement report, the timeline, the kinship query, reconciliation, clustering and the static site) still read them; extraction refuses and counts any spouse claim.

Amended by ADR-0040 (2026-10-24), carried out by its build:

- "`ended_by` a divorce, an annulment, a partner's death" reads "`ended_by` a divorce, an annulment or an event of unstated kind, or `ended_by_death_of` the partner who died" (ADR-0040's Q2).
- `ended_by_death_of` is written only where a source specifically states that the couple were married when that partner died:
  - a survivor's widow or widower word that names the late spouse ("Witwer der Cäcilie Löbig geb. Tarle", "вдова Вашего покойного брата Рудольфа");
  - a death record that calls the deceased the survivor's spouse ("Ehefrau des Eugen").
- "His late wife", a card's "Husband: … died 1931", a GEDCOM family plus a partner's DEAT, or a marriage and a death in two documents give no end. Views derive the end from the partners' death spans, labelled as derived, and never write it (ADR-0040 §2.6).
- The link is death evidence for the partner it names (ADR-0040's Q9).
- A widow's or widower's marker that names the late spouse gives the survivor's `civil_status` `widowed` and the union end, and no death statement for the late spouse. The late spouse's "died by" date is derived (ADR-0040's Q5).

**The GEDCOM adapter makes unions (ADR-0036 §5).** A family's couple are its first two `HUSB` and `WIFE` lines, in whatever combination (a `HUSB` and a `WIFE`, or two `HUSB`s or two `WIFE`s, as GEDCOM 5.5.1 exports write a same-sex couple, counted), and each is the children's parent as its tag states: a `HUSB` their `father`, a `WIFE` their `mother`; a `HUSB` is read before a `WIFE`, whatever their order. A third is counted (`FAM.HUSB`, `FAM.WIFE`), not read, and a line that restates one before it (same tag, same person) is counted and passed over. A family with two partners is a `marriage` when a `MARR` of it states a wedding, or when a `DIV` or `ANUL` states its end with no such `MARR` (a marriage with no wedding, counted), otherwise a `partnership` (the export gives Felix and Ida no `MARR`, so theirs is a partnership); its couple are its participants with the role `spouse` or `partner`. A family whose two partner lines are a `HUSB` and a `WIFE` naming the same person gives no union and no parent claim, counted. A `MARR` states its wedding as a `DIV` its divorce, by a `Y` or a `DATE` or `PLAC` with a value: a `MARR N`, or one that states nothing, makes no wedding and is counted. The family's `MARR`s of one kind are one wedding, which the union is `started_by`: a `civil_wedding` or a `religious_wedding` where the `MARR`'s `TYPE` names the ceremony (`civil`, `religious`, `church`, and their German forms), else a `wedding`, which a `MARR` whose `TYPE` names no known kind joins, that `TYPE` counted. Its `DIV`s are one divorce and its `ANUL`s one annulment, which the union is `ended_by`, each `PLAC` the event's `location`, and a `DIV Y` an undated divorce, counted, as is one whose `DATE` gives no date. Each date and place of each record is a claim of its own on that event: its `point_in_time`, with the range and circa its `DATE` states. A `FROM … TO …` on a `MARR` dates the wedding by the `FROM` and an end of unstated kind (an `event`) by the `TO`; on a `DIV` or an `ANUL` it is the event's own `start_time` and `end_time`, as an imprisonment is dated. No end is inferred from a partner's `DEAT`. A `SOUR` beneath a `MARR`, `DIV` or `ANUL` cites that event's claims and the union's claim that points to it; the family record's own `SOUR`s cite the couple's claims.

A statement that holds for a period, such as a residence, an occupation or a membership, is dated as Wikidata dates spouse (P26); a marriage is dated by its events (ADR-0036), and the retired spouse statement's dating below is the convention its readers still interpret:

- **A retired spouse statement's `start_time` dates the marriage**, and its `end_time` the date it ended (a divorce, an annulment, or widowhood, when the source dated the end itself): under that convention, Leopold and Agnes's marriage, from 8 February 1947 until the divorce of 2 January 1957 per the judgment, was a spouse statement with that start time and end time, each partner's carrying the dates its source gave. Nothing writes one now: the judgment's marriage is a `marriage` `started_by` its wedding and `ended_by` the divorce. A move in and a move out date a residence by `start_time` and `end_time`, and the GEDCOM adapter reads a residence's or an occupation's date period (`FROM 1939 TO 1952`) as its start and end time, each with the range its own date gives, and with one circa when either end is approximate.
- **`point_in_time` on a spouse or residence statement dates an observation**: a date at which the source presents the marriage or the residence as holding (a directory's listing, a census) without dating its start or end. It never carried a wedding date. A source that merely named a spouse, without dating the marriage, gave an undated spouse statement: the document's own date was no observation of the marriage (Ida's registration card of 1945 names Felix, dead since 1931, as her husband). Now such a source gives a union with no date, and the document's date is still no observation of it.
- **Each end has a range of its own.** A statement has one start and one end, and a source may bound either, so each end takes its own pair of qualifiers, as on Wikidata since `latest start date` (P8555) and `earliest end date` (P8554):
  - a start runs from its `earliest_date` to its `latest_start_date`;
  - an end runs from its `earliest_end_date` to its `latest_date`.

  `earliest_date` and `latest_date` are thus the outer bounds of the period: the earliest it can have begun and the latest it can still have held. A marriage "between 1946 and 1947" is a start time of 1946 (the first date, as a range is stored) with an earliest date of 1946 and a latest start date of 1947; a divorce "before 1958" is an end time of 1958 with a latest date of 1958. An earliest date never bounds an end, nor a latest date a start.

  These pairs bound start and end time _qualifiers_. An entity's own `start_time` or `end_time` claim, such as the firm's founding in 1863 or the start of Leopold's detention in 1939, is a date value like a date of birth: `earliest_date` and `latest_date` bound it, and the disagreement report compares it as a single-valued date. A latest start date or an earliest end date never qualifies such a claim.

- **On a statement with no start or end time**, `earliest_date` and `latest_date` bound its point in time, as they bound a date value: a residence observed "between 1938 and 1939" is a point in time of 1938 with those two dates. A point in time beside a start or end time has no range, since there those dates bound the period.
- **Circa** (`sourcing_circumstances`) qualifies the whole statement. On a spouse statement with a start and an end, it says that the source gives at least one of them approximately, and cannot say which, rather than drop it (rule 5). So the person timeline shows it beside the statement's start and its end alike.

The disagreement report compares a residence's or a spouse's start and end times, each through its own range ("Contradictions" below); the person timeline (`src/yizkr/queries/person-timeline.rq`) lists each start, end and point in time with the range stated for it, which the static site's timeline page and feed show beside the date, each bound under its qualifier's label ("1946 (earliest date: 1946; latest start date: 1947)"). An event's own start and end time are rows of their own there, each bounded by its earliest and latest date ("imprisonment (start time)", "imprisonment (end time)"), each once under all the event's types, and on the timeline of each participant whose participant statement is not deprecated (a preferred participant or type hides no other); and the extraction prompts give the extractor this convention for residences and other periods, and date a marriage by its wedding and end events instead.

## Persecution and displacement as events (see ADR-0014)

Forced removal, detention, and freeing are **events**, not relations: `deportation`, `imprisonment`, and `release` are event subclasses that reuse the event machinery (`participant` → person, `location` → destination, `point_in_time`/`start_time`/`end_time`). "Deported to Klurnau" is a deportation event, never a `deported to` property — the same shape as the reconciled deportation events already in the graph.

These relations are therefore **not** open-schema gaps (ADR-0013): a `deported to` or `imprisoned at` line in `gaps.csv` reports something the vocabulary already holds, so it is an extraction mistake to fix, not a signal to grow the schema on.

## Identity and reconciliation (ADR-0007)

The approved contract separates source bytes, placements, readings, local mentions and persistent entities. Labels, filenames and a particular clustering output are not durable identity. The rules below describe the current mapping and review machinery; safe incremental identity changes and recovery follow the [ingestion contract](INGESTION_CONTRACT.md) and remain work under #130 and #142. Approval of the policy does not make the current one-map restriction safe to remove.

- The current writer appends each document's name variants as item **aliases**. Additional aliases can aid matching but can also carry mistakes; the approved correction contract is broader than this implemented append-only behavior. Where a source _types_ a name (birth, married, nickname, official), it is additionally recorded as a referenced statement; a further name form whose type the source leaves open is recorded as a referenced `name` statement — see "Names".
- A scratch run clusters every document's mentions across the corpus before any write (the clustering stage, `pipeline/clustering.py`, ADR-0025). It keys and judges on each mention's record, never on a label's wording (ADR-0035 §7): a person's given names by their standard forms and as written, with its surnames and its kin's; a place's names and address as written, its containers (its record's, and those its manifest's `part_of` and `location` claims give) compared as one set; an organisation's proper names, else its kind with its places, which agree only when they would link as places or one lies in the other; an umlaut also written out (DIN 5007-2). A person, place, organisation or family without a record (none given, or one extraction set aside under ADR-0035 §5, before the alias cleanup) meets only its exact name, never one its document gives as an appellation (two people called "Oma" never meet by it), and never merges; so a document's mention whose record was set aside never meets the GEDCOM export, whose people and places all have records; the kinds that take no record (occupations, vessels and the like) still merge on an exact name. A union is keyed by its couple, and its weddings and ends by union, kind and date (ADR-0036 §3). A birth's or a death's date belongs to its principal alone, and one with no principal, several, or one whose own date of that kind conflicts with it, is nobody's and merges with none. (Amended by ADR-0040, 2026-10-24: a birth's or a death's date is a statement on the person, read as any of their dates, and "died by" dates are read through the shared derivation. There is no birth or death event to key, and a `date of death` of unknown value dates nothing of its own.)
- Admission to retained state requires review of the affected identity assignments. New equivalences are explicit in the reviewed assignments; merges/splits of existing entities require affirmative confirmation. Approved matches resolve new claims to the existing item rather than minting a duplicate. Disposable rebuilds can use unratified machine assignments and confer no human confirmation.
- Where equivalence of two _existing_ items is itself a judgement a source supports, it is an ordinary referenced statement: `said to be the same as` (Wikidata P460), citing the artifacts whose content supports the identification and the reconciliation run. True duplicates are curator-merged instead.
- The current candidate filter prunes pairs on recorded structural evidence of distinctness (ADR-0017): an irreflexive kinship edge between them, or one place transitively inside the other. It uses the graph's referenced claims, not mere name dissimilarity; unknowns stay candidates. Such claims are evidence, not a guarantee of historical truth, so a mistaken structural assertion can also exclude a legitimate candidate. Deliberately excluded is a date disagreement: that is healthy coexistence (ADR-0002) to surface, not proof of distinctness. The containment it reads is the edges the inconsistency report follows: a `part_of` or `location` claim a source states, not deprecated. A rejected equivalence between two places, one inside the other, is a `distinct` verdict and nothing more: the adjudicator names no container (ADR-0038 §8.2), and a reviewer who knows the containment records it by citing the source it rests on.

## Contradictions

The current contract preserves genuine incompatible assertions, including contradictory passages in one source, and distinguishes them from alternative machine readings or corrected mistakes. Summaries may group evidence when they reveal material disagreement and provide access to its sources. The report described below has a narrower implemented scope: different-artifact comparisons. It is not a complete test of whether the archive contains disagreement, and two separately registered witnesses are not necessarily independent corroboration.

- Competing values for the same property coexist as separate statements at **normal rank**, each with its own references.
- Rank changes are curator actions logged by MediaWiki history; no feature requires a preferred value. The current correction path may require deprecating a mistaken reading to remove it from comparisons, which is a curation-interface limitation, not a requirement that every user manipulate ranks.
- Disagreement _reporting_ pairs values that **different artifacts** attribute (ADR-0023 §4). Two queries fetch what it compares, with no pairing of their own: `disagreement-report.rq` lists every statement of the compared properties with its rank, value, dates and stated-in sources, and `place-containment.rq` the recorded containment edges and merge redirects. `yizkr.disagreement` compares them in Python, one function per rule below (ADR-0033); the static site's inconsistencies page shows its rows, each value with every source that states it. Two readings of one artifact (a curator's correction beside the machine reading it corrects) are not two sources, and a page fragment counts as its artifact. An image that a deck or a compilation embeds is an artifact of its own, not a fragment, so a compilation and an original excerpt it embeds are two sources (ADR-0008). A statement with no stated-in source attributes its value to no artifact and takes no part. (The unreferenced-statements report lists only a statement with no reference at all, not one whose references lack a stated-in source.) A deprecated statement is left out; a preferred one is listed like any other, so the report never needs a preference.
- It compares values only for properties that can hold at most one true value per subject (dates/places of birth and death, birth name, an event's or other entity's own point in time or start/end time, a document's `inception`, a place's identity properties), and for the parents. A child may have two fathers or two mothers (a GEDCOM family of two `HUSB`s or two `WIFE`s, ADR-0036, amended by #353), so a source that names two parents of one gender states them together: its two values never disagree with each other, nor with a source that names one of them. Two sources disagree on a parent only when each names one the other does not: a source naming, say, Leopold and Rudolf as Eugen's fathers disagrees with no source naming one of them, but a source naming only Leopold still disagrees with one naming only Rudolf, and a source naming Felix with each. A curator who corrects a parent deprecates the reading corrected, which is then left out; a correction left at normal rank beside the reading it corrects reads as that artifact naming both, so it hides the corrected value's disagreement with another source that names the reading's parent. A document's date of making can come from more than one source: the document itself and, read as a curator's claim, a container's caption (ADR-0039), so two sources that date one document differently are listed side by side, each with its source; as for any other date, one whose span lies inside the other's differs only in resolution (below). (Widened by #626, 2026-10-24, ADR-0039 §10.2: the date of making may also come, with no curator, from a container whose passage conveys it, such as the booklet's translation of a letter's dateline, or from an export's record of an object; these are compared the same way.) A name compares as text: spellings that differ only in letter case (a sharp s written SS among them) or language tag are one value, listed once with the sources of all of them. Properties that legitimately accumulate values over a life — spouse, residence, married names, nicknames, official names, names of no stated type — are multi-valued by nature: two spouses asserted by one source are remarriages, not a contradiction (their start/end qualifiers tell them apart). For one residence place or one spouse (through merge redirects), the report compares the start and end times that different sources give (in Australia from 1939 per one source, from 1938 per another), so a return to a place a person had left shows as a start-time disagreement. A point in time on a residence or spouse statement dates an observation, not the residence or the marriage ("Marriages, residences and other periods"), and is not compared.
- **Current parent and death comparison (ADR-0040):**
  - Parents are compared within one kind. A pair of parent values is set aside when any non-deprecated statement gives either value a `parentage` other than birth, so a birth father named by a register and an adoptive father named by an adoption order never disagree. A parent with no kind stated is compared as a birth parent.
  - A `date of death` of unknown value states no date, so it is set aside and never listed.
  - A derived "died by" date is compared, labelled as derived, as a range open at its early end.
- A date whose span lies inside another's and a place the graph records inside the other differ in resolution, not substance, and are not reported. A place lies inside another along a path of `location` and `part_of` claims, each one a source states (with a stated-in source) at normal or preferred rank, whatever time it carries: one path at any time is enough (ADR-0038 §5). A date's span is the whole period its precision names (a month, a year, a decade, or a century as Wikibase counts it, which holds 1900 in the 19th century and 1800 in the 18th: "Uncertainty and time"), or the range its source states with `earliest date` and `latest date`, open-ended when only one is given: 1909 and 16 March 1909 agree, as do "between 1938 and 1939" and either 22 June 1938 or 3 September 1939, and "before 1926" and 1912, while "after 1945" and 1941 disagree. The 19th century agrees with 1900 and with the 1890s, and disagrees with 1800 and with the decade 1900–1909, which reaches past it. A stated range is never widened back to its precision (rule 5): 1939 stated "between September 1939 and 1 October 1939" and August 1939 disagree. A precision coarser than a century names no span. A range dates only a time: on any other value, such as a place, a person or a name, it sets nothing apart. Two dates stored alike are compared through the ranges their statements state: "before 1945" and "after 1945", both stored as 1945, disagree; with the same stated ranges, or none, they differ at most in resolution, as do dates stored alike whose spans nest: the 1890s stated as a decade, as "between 1890 and 1899" or as 1890, all stored as 1890. A statement that carries two earliest (or latest) dates states its value once per range, and each is compared with other statements' values; its own readings alone are one claim, never listed against each other, however many artifacts cite it. A residence's or a spouse's start and end times are compared like any other date, each through the range its statement states for that end: a start from the earliest date to the latest start date, an end from the earliest end date to the latest date. So a marriage begun "between 1946 and 1947" and one begun on 8 February 1947 differ only in resolution, while a latest date, which bounds the end, sets no start apart.
- **Current uncertainty storage (ADR-0023).** The graph records source vagueness through circa, ranges and precision. Extraction confidence is not written as a graph value; critique findings and their axes (`subject`, `predicate`, `value`, `existence`) remain review/process information. `under-witnessed-statements.rq` selects low-scrutiny machine writes structurally, not by calibrated confidence or independent corroboration. Bulk acceptance is recorded in the reviewed CSV and edit history. The contract requires these kinds of information to remain distinguishable; it does not prescribe that every future process record must use this storage arrangement.

## Living persons and privacy (see ADR-0020)

The archive and its exploration views are private by default and serve authorized audiences. Retaining an assertion does not authorize disclosure. The existing non-privileged export is a filtered view, not a public-safe edition: retained text can mention living people. Audience-specific release and the final privacy requirement/cutoff decisions remain separate work under [#163](https://github.com/WillHirsch/yizkr/issues/163), [#70](https://github.com/WillHirsch/yizkr/issues/70) and [#72](https://github.com/WillHirsch/yizkr/issues/72). The implementation rules below remain in force; this policy update changes no cutoff or disclosure gate.

- **Current runtime eligibility.** There is no stored living flag. `yizkr.core.privacy` evaluates death evidence and birth dates when the non-privileged export or private site needs the possibly-living determination. The export and site share that person-evidence calculation; the export also applies the additional structural filters below. This is a disclosure mechanism, not a verdict on whether every retained historical assertion is true.
- **Current death evidence** is a sourced `date of death`, `place of death`, `cause of death`, `place of burial` or `age at death`, or a qualifying curator-made death event. It needs neither a complete date nor a place. A `date of death` of unknown value counts, while a deprecated statement or a no-value statement does not. A union's `ended_by_death_of` counts for its named partner. Derived "died by" dates are not themselves death evidence (ADR-0040).
- **A curator-made birth or death event is its one principal's own** (ADR-0020; ADR-0040). A death event releases only the single participant its `participant` statements name in the role `principal` (`object_has_role`, read from the statement's qualifier, not the truthy triple), through a statement at the best rank that states no other role; an informant or a witness at someone else's death stays possibly living. A death with no principal, with several, with one of unknown value, or with no role stated at all is nobody's own and releases no one. A dated birth event's `point in time` is a birth of its principal, read as a `date of birth` is: it may release a principal born only by it, and an 1850 date of birth beside a 1990 birth event keeps the person possibly living. A birth event that is nobody's own only adds its date to the births of participants who have a birth already, so it can only keep them possibly living. The export and the site read both through `yizkr.core.privacy.read_evidence`, so they decide each person alike. Extraction and GEDCOM batches make birth/death statements on the person, not events; this event handling applies to curator-made items.
- **Current review interface.** There is no `living` column in the review CSV. A curator records supported death information as an assertion rather than setting a flag. Authorizing retention is distinct from authorizing disclosure; these automatic eligibility rules do not replace an audience decision.
- The export (`yizkr backup`'s `nonprivileged.nt.gz`, a non-privileged view, not a public copy) is **conservative**: a person enters it only on positive evidence they are not living — any death evidence above, or births beyond the cutoff (`--cutoff-years`, by default `DEFAULT_CUTOFF_YEARS` in `yizkr.core.privacy`). **Unknown means excluded.** The graph filters remove item references to excluded people (including other people's claims about them and orphaned provenance nodes), and a transcription excerpt — a raw source quotation — leaves only with a statement it attests. A statement whose value, or any qualifier's value, is an item left out goes whole, on a kept item too, with its rank, qualifiers and references (ADR-0020, as amended by #364): an appellation of a released person whose `perspective` is a possibly living relative goes, its text included, and a statement naming a possibly living partner takes its start time and its excerpt with it. Its truthy triple goes too, unless a kept statement of the same item and property, at normal or preferred rank, gives the same value; a statement of unknown value that goes takes every truthy triple of unknown value of its item and property, as the export does not read which one it gave (it does not reproduce Wikibase's blank-node labels). A reference or value node that a kept statement uses too stays, its excerpt included, once, in the first kept entity's block that uses it, where the query service's munger reads it (ADR-0020, as amended by #412).
- **Who is a person fails closed too** (ADR-0020, as amended by #344). An item is a person when it has any person evidence, read at every rank, deprecated included: a `human` type; a statement of a property only a person has (a birth, a death or a burial, kinship, a birth or married name, a nickname, a name of no stated type, what they are referred to as, a sex or gender, a number of children, an occupation, an employer, a school, a citizenship or a residence); being the value of a kinship property or of `gave refuge to`, in a statement or a qualifier; or taking part in a birth, a death, a marriage, a migration, military service, a deportation, an imprisonment or a release. So a deprecated or outranked `human` type hides no one. An official name, a religion or a membership, a part in an event of another kind, a depiction, an identity judgement (said to be the same as), a perspective or any other qualifier, and the values of place, organization, artifact and vocabulary properties mark no one. A type is read through the redirects it names, so a class a curator merged into `human` types as `human`. An item typed as a vessel, a military unit or an organization at normal or preferred rank is taken at its type on its part in a person event: any other evidence makes it a person, a `human` type at any rank included. An event is taken at its type on the death it states (#577): an item typed as an event (`event` or a class the manifest makes a subclass of it, a `death` among them) at normal or preferred rank is not a person on its `date of death`, `place of death`, `cause of death` or `place of burial` statements, of each of these it has a truthy value of, so a death event that states its cause or its age gets no person page and is no person to the export. That truthy value is death evidence as the check reads it, so the item would be released were it a person: setting it aside releases no one the check would keep. Any other evidence still makes it a person, a death statement with no truthy value beside it (deprecated, or of no value), a `date of birth` or a `human` type at any rank included, and an item typed as a family too stays listed and badged as every family is. The event's statements stay on the event, and its principal's timeline shows it as before. (Amended by ADR-0040, 2026-10-24: with no death events from extraction, this set-aside guards only an event a curator makes, and it stays. Validation and the writer refuse a death or birth property on any subject but a person, `human` or `unclassified_entity` (ADR-0040's Q11).) A family is not taken at its type: its label is a surname, and a person known by a surname alone can be typed as one. The export reads this evidence from its own dump and **keeps a person only once the check has released them**: an item the check never assessed is dropped, and a redirect goes with the item it redirects to.
- **What states no type is left out of the non-privileged export**, whatever else it holds, so no type at all hides no one either: an item none of whose `instance of` statements at normal or preferred rank names an item (an unknown or no value, or a type a curator deprecated, names none). The vocabulary is kept: the manifest's items, and every item that is the value of an `instance of` or `subclass of` statement. An item left untyped (a write cut short between its label and its type, a reference that gives no kind) is missing from the non-privileged export until it is typed. A run item left so is typed by the next run that finds it ("Artifacts and registration").
- **A family never enters the non-privileged export** (ADR-0020, as amended by #344). A family stands for its people, the people recorded as `member of` it, and is private while any of them may be living. The model cannot state that a family's membership is complete (there is no household statement enumerating occupants, above), so the export leaves out every item typed `family` at normal or preferred rank, whatever it holds, released or not, and the site badges it. #374 holds the full rule, with a way to mark a family's membership complete.
- **An event goes with its participants** (ADR-0020, as amended by #363). An event's date and place are its participants' too, and its label is written after them, so the export leaves out every event, whatever its kind, that has a `participant` statement at any rank whose value it leaves out, a redirect to one included, or one with a qualifier that names such an item, whatever the statement's value, an unknown one or none included (#364). An event goes, too, with any item that one of its statements names, as its value or a qualifier's, whatever the property: a divorce `carried out by` an organization left out for its person evidence goes with it (the orchestrator, 2026-10-02). The rule follows only items left out to protect people: an untyped place, or a family (or any item named a `member of`) with recorded members all released, names no one, so a released person's birth at an untyped place stays, without the statement naming it; a family with a member who may be living, or that names no member, takes the event with it, and so does an untyped item that may be a person (through redirects), that the participant or unattended rule leaves out too, or that names an item left out to protect people. Such a group whose members are all released takes part in an event harmlessly, as a released person does, except in a person kind of event, which is its members' own, however the event names it (as a participant or, say, `carried out by`). Members are read through the groups among them, through redirects, ending on cycles: a member group with a member not released, that names no one, or that has person evidence and was not released by the check makes the outer group take events with it, and so does a `participant` of unknown value. A person named a `member of` (a household recorded under its head) is a member whose standing counts, and whose own members are read too; a person is never a released group. An event that names the released head of a household stays, whoever is recorded under that head: a released person is judged on their own standing alone, and only a group by its members. An untyped item with members is judged as a group, on its members. A class the dump makes a subclass of a person kind of event is a person kind too, everywhere in the export's reading of the dump; the check's own selection of people does not follow such classes, so a participant of one that the dump alone makes a person is left out as not assessed, failing closed. An event is an item typed `event`, a subclass of it or a person kind of event, or an item with a `participant` statement, but never a union (a partnership or a marriage, or a subclass of one), whose events go with it and not it with them, nor an item typed human at normal or preferred rank, unless typed a family too (for the participant rule too). An event so left out may itself be a participant, or named by another event, and the rule applies again. An event of a person kind that names no participant (none, or only one of unknown value, however qualified: what a qualifier names, a role included, is no person evidence and attends no event on that alone) is left out too: whom it happened to is unknown; and so is an event of any kind that has participant statements, every one of an unknown value or none (the orchestrator, 2026-10-02, failing closed as ADR-0036 §6 does for unions), while one of no person kind with no participant statement at all names no one and stays. And the events that start and end a union it leaves out go with the union (`started_by`, `ended_by`; ADR-0036 §6), a partner's own death aside. (Amended by ADR-0040, 2026-10-24: "a partner's own death aside" reads "the partner named by `ended_by_death_of` aside". It is no bound and stays out of `UNION_BOUNDS`, and the partner follows the person rule through `PERSON_VALUE_PROPERTIES`. A partner released by that end alone is kept when the union is left out, though the export then lacks the statement that released them.)
- **Retained free text is not public screening.** The non-privileged export keeps a released person's labels, descriptions, aliases, names, statement values and the excerpts of retained references, along with text on other retained items. That text can mention a possibly living relative. The audience policy permits this in the existing non-privileged view; it does not authorize a public copy. Families and untyped items remain subject to the exclusions above.
- **Source text and process exclusions.** The export removes extractor judgement notes and entire `caption` statements with their unshared references. For a document-subject statement on held media that another document states, or on an artifact `part of` its stated-in source, it removes the container's reference and excerpt. A statement with another retained evidentiary reference can remain; one with none beyond the run reference, or with a text-valued qualifier that may hold the container's words, is removed whole. A document-subject statement on an un-held mention item follows its source's ordinary rules. An unreadable triple is dropped; a dump with a sitelink or an unsupported property datatype makes export refuse (ADR-0039).
- The check runs on the query service, so the export waits for the query service to hold the dump's revision of every item and property, and **refuses to run** while it does not, or when the graph changes during the check. The match is exact: an entity whose revision never reaches the query service keeps the export refusing, naming the entity, until that entity is edited again or the query service is reloaded from a full dump.
- **Births fail closed** (ADR-0020, as amended by #334). A birth releases a person only at the latest year it allows, and only when every `date of birth` statement a curator has not deprecated does so by the cutoff, never one value sampled from them. A statement's latest year is its latest date's, when it states one, as a stated range bounds a date ("Contradictions"); it has none when it states only an earliest date, since "after 1850" is open at its late end. Otherwise it is the last year its value allows at its precision: 1899 for the 1890s, and 2000 for the 20th century, with centuries and millennia counted as Wikibase counts them, except that a round hundred is read as the century it opens, so 1900 at century precision allows 1999. A statement whose value or an earliest date lies wholly after its own latest date is read without that latest date, which fails closed. A statement allows no latest year, and keeps its person possibly living, when a latest date in it cannot be read, or, where no latest date bounds it, when its value is unknown, unreadable or coarser than a millennium, or it states only an earliest date. A readable latest date bounds even a birth whose value is unknown, unreadable or coarser than a millennium. A birth before the common era or in a calendar other than the proleptic Gregorian, as the value or a bound, stops the check and with it the export, naming the person and the statement (ADR-0034): it fails closed.
- The private static site (`yizkr publish-site`) includes everyone but badges each subject the export would drop ("possibly living — never in the non-privileged export"), using the same runtime call, except a person with no type, whom the export leaves out even when released; the site shows no badge. A family it lists is always badged. Its people are the items with person evidence, selected as the check selects them; the export also drops what the site lists as no person, an untyped item without person evidence, a family without person evidence, a redirect and an event that one it drops took part in.
- **Current death and union displays.** The person page shows each `date of death` with its sources, an unknown value as "died (date not stated)", and derived "died by" dates labelled as derived. An unknown value appears beside a dated death when one is recorded, otherwise under "No date stated". A burial is dated by its `point_in_time`; the map includes places of birth, death and burial. A union shows its stated end and sources, or a derived end when none is stated. On the timeline, an end by death appears beside that partner's dated death or under "No date stated"; an end by an event appears at the event's date. Curator-made birth/death events appear only on their principal's timeline, and an undated curator-made death remains visible through `UNDATED_DEATHS_QUERY`. Display can show an assertion that does not satisfy the separate disclosure test; a displayed death does not override the possibly-living badge.
