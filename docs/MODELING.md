This guide describes the current Wikibase conventions and implementation limits; it does not imply that every approved retained-state capability is implemented. ## General approach

People, places, artifacts, events and periods can have independent identity where useful. Dates and uncertain intervals use values and qualifiers; not every date needs an item. Ordinary vocabulary additions preserve evidence and identity, while new domain behavior may require code or a migration. The concrete conventions below describe the current implementation, not a promise of arbitrary schema extension without work.

**Retained-state limit:** item creation has durable, instance-qualified bindings and interrupted-write recovery independent of display terms. The shared authority records reviewed mention assignments, verified migration and graph-readable identity origins. A separate [assignment-aware route](IDENTITY_REVIEW.md#apply-reviewed-historical-claims) writes explicitly approved historical claims to existing entities and records their exact graph support. Legacy map writers still require their map guards. [Protected later-cohort additions](IDENTITY_REVIEW.md#apply-later-cohort-identity-additions) reuse these authorities under server exclusion. Incremental document orchestration remains under #723 and retraction/split under #142. A retained instance must not be reset to bypass these limits. See [recovery and its boundaries](ARCHITECTURE.md#item-creation-and-interrupted-write-recovery).

- The schema is self-describing: properties and classes are minted as Wikibase properties/items in-instance.
- Mirror Wikidata property _semantics_ where a good equivalent exists (instance of, date of birth, spouse, residence, depicts, coordinate location, start/end time, stated in...), using local P-ids. The vocabulary is declared in `src/yizkr/model/manifest.yaml` and minted by `yizkr bootstrap`, which maintains the mapping table (local id – Wikidata id) on the wiki page `Project:Model mapping`. Local P/Q ids are per-instance and never recorded in the repo.
- Every entity gets a label and a short description; name variants go in aliases. English labels are the bootstrap's idempotency key: a property's and a manifest vocabulary item's label names one entity alone, and renames must happen on the wiki and in the manifest together. Other items may share a label: two people of one name are two items under one label (homonyms). The wiki client's label index gives such a label the numerically earliest of its items, and keeps every holder, and fails only where a label must name one item alone: a vocabulary item's (the vocabulary's whole read, the bootstrap) and bootstrap lookups that require a unique vocabulary label. The vocabulary is read bounded where it can be (#507): the ids `Project:Model mapping` gives the manifest's labels, each checked to carry its label, 50 a request. That read sees only those ids, so another item under a vocabulary item's label goes unseen there, and the bootstrap, which reads every label, refuses it. When the page is missing, lacks or repeats a manifest label, names one id under two labels, or an id is missing, a redirect or carries another label, the vocabulary reads every label whole. No extracted entity is found by its label (#109): the writer uses its identity-map operation and verified server binding (below).
- **Current mapping: one item per cluster of the identity map.** Every local mention must belong to the supplied map; otherwise the writer refuses the batch before mutation (`UnmappedMention`). An approved equivalence can name an existing QID explicitly. Reviewed batches use the original extraction as `mapped_from`, so dropping claims does not change which mention a local ID denotes. A cluster creation operation reserves an opaque entity ID and binds it to the resulting QID in the shared server registry. Repeating the same operation reuses that binding after label or description edits. The initial label comes from the cluster’s mentions; other names become aliases, and each source can contribute referenced kinds or type hints. Rebuilding disposable state establishes a new deployment generation and does not promise stable QIDs.
- **Legacy map writer limit: one identity map per deployment generation.** The registry reserves the map hash in an immutable server record before mapped entity writes. Run labels and descriptions also display map provenance, and the writer retains its checks for other recorded maps. Migration records verified assignments and origin references; it does not switch a legacy writer to another map. The explicit assignment-aware route uses existing verified bindings and scoped claim approval, retaining assignment roles and support receipts without minting entities or adding implicit aliases/types. Matching generated terms cannot migrate a cluster. Scratch clustering supplies its map from admitted document batches; mapped writes refuse unmapped mentions. Scratch reset/reuse guards remain, and explicitly disposable fixtures can disable the one-map restriction for isolated tests. Display collision rules do not establish identity.
- An extracted entity’s initial `wbeditentity` request includes its label, description, aliases and sourced kind/type hint. Its creation revision carries the reserved intent marker. A lost response can leave a completed item: recovery verifies that revision and records the QID receipt before continuing. Registration and process items that require their own QID for self-references finish those statements separately on resume. No multi-item batch is atomic.
- **An item’s initial description is its cluster’s source descriptor.** It describes the kind and the sources naming it, such as `human named in a genealogical report` or `human named in 3 sources`. Same-named clusters receive deterministic ordinal suffixes to satisfy Wikibase’s label/description uniqueness rule. Descriptions contain neither extracted biographies nor artifact titles, QIDs or digests. They are display text: the registry supplies identity, existing curator descriptions remain unchanged, and an unbound item with matching display terms triggers migration refusal rather than adoption.
- Wikibase keeps labels, descriptions and aliases trimmed and normalized, with a 250-character limit. The writer normalizes new display terms, fits long terms with a digest suffix and avoids a description identical to its label. Registration and alias hygiene use the same term conventions. These transformations do not change a bound entity’s identity; lookup uses its creation binding. Statement values retain their own validation and comparison rules.
- Wikibase puts a term, and every text, in NFC by the tables of Unicode 15.0 (ICU 72.1 in the wikibase/wikibase:7 image), and the writer by Python's (14.0.0 on Python 3.11). Unicode's normalization stability policy makes the two agree on every text whose characters Python's tables assign, so the writer sends no term that holds a character they do not, noncharacters aside, read whole, past the cut too, so that no cut of such a term is sent either: a combining mark assigned since, such as U+1E08F, the combining Cyrillic Byelorussian-Ukrainian i, may take another place in the instance's NFC. An alias or a type hint that holds one is left out, never changed, and the write's result names it in `refused_terms`, with a warning. An entity's description is the writer's source descriptor, made of manifest keys alone (above), so no description is named (#86). An entity whose label holds one is neither found nor minted, and each claim that mentions it is refused. The registrar makes no alias of a title that holds one, and content-tags a new item's label made from one, as it does a taken label, so two same-named copies stay two items whatever form the instance keeps the first one's label in. A claim refused for its text, as a misplaced document subject (ADR-0035 §3.4), or with an entity that may join neither the item under its label nor the one under its tagged label (ADR-0010), mints nothing. A manifest record whose local refs only such refused claims hold has nothing of it sent, so its aliases and type hint are not named in `refused_terms` either (amended by #444, 2026-10-03). A run item's label holding one, an extraction run's or the place-hierarchy pass's, or an extraction run's description, raises ValueError before the run item is looked up, and so before anything is written, so unsupported display terms never reach the graph. The interpreter's tables must be no newer than the instance's, which a unit test checks (writer's INSTANCE_UNICODE; ADR-0010, #431).
- The current bootstrap references schema-level statements (such as the subclass hierarchy) to the _model manifest_ item representing `src/yizkr/model/manifest.yaml`. The approved provenance policy requires accountable origin and versioning for schema and operational records; it does not require every such record to use a source-artifact citation. This encoding remains until a supported replacement is implemented (ADR-0003).

## Core classes (items, via "instance of")

- human
- place
- time period (linked to PeriodO definitions where applicable)
- event (migration, military service, a wedding with its subclasses civil wedding and religious wedding, a divorce, an annulment; birth and death classes are available for curator-made events, not extraction — ADR-0036, ADR-0040)
- partnership (a couple's relationship of any kind, for two people a source presents as a couple without saying they married), and its subclass marriage (Q8445): each is an entity, not an event. Its couple are participants with the role `partner` or `spouse`; `started_by` links its wedding and `ended_by` a divorce or annulment (ADR-0036). `ended_by_death_of` links the partner whose death ended it, only where the source states that they were married when that partner died. Otherwise views derive the end without writing one (ADR-0040).
- artifact (subclasses: photograph, certificate, letter, census page, newspaper clipping, presentation, genealogical report, address book, ...)
- organization (an agent — company, bank, committee, government body, school, congregation; distinct from place — see ADR-0012)
- family (a named family or household unit — ADR-0014)
- vessel (a ship; e.g. an emigration vessel — ADR-0014)
- legal instrument (a cited law, decree, gazette, or register — ADR-0014)
- military unit (a regiment, brigade — ADR-0014)
- occupation (values of the `occupation` property; labels keep the source's wording)
- unclassified entity (the open-schema holding class — see [ADR-0013](EXTRACTION.md#schema-gaps-and-critique-adr-0013))
- artifact fragment (a page, crop, or region of an artifact)
- extraction run (a bound write operation with recorded producing stages and application context; see [run provenance](RUN_PROVENANCE.md) for model/configuration/version facts and immutable record references)

**Manifest descriptions are extraction-prompt surface**, not only documentation. Every property and item in `src/yizkr/model/manifest.yaml` carries a description, and the extractor is shown it verbatim beside the key: a property's description is what tells the model which way a relation points (`employer` takes the organization, not the employee) and what kind of entity the value must be (`location` takes a place). Write them for that reader as well as for a human.

Items flagged **`entity_kind: true`** are the kinds the extractor may type a document-mentioned entity as (the [ADR-0007](EXTRACTION.md#entity-first-and-chunked-extraction-adr-0006-adr-0007) manifest pass), and the prompt renders that set from the manifest rather than restating it. Artifact types, controlled-vocabulary values (`circa`, `male`), and infrastructure classes (`artifact_fragment`, `extraction_run`) are real classes but not entity kinds. A new item is not offered to the extractor until it says so. The classes of entities that are no entity kind, `artifact` and the artifact types, `time_period_class` and the infrastructure classes, are marked **`entity_class: true`**; with the entity kinds they are the manifest's **kind keys**. The manifest does not load when an item in the subclass hierarchy is neither, or when an entity kind is also marked `entity_class` (amended by #462, 2026-10-05). A controlled-vocabulary value is neither. Outside the hierarchy nothing else tells a class (`time_period_class`) from a value (`circa`), since each may be the one item its property accepts, so the mark there is the manifest author's to set, and a test pins the classes it holds.

**Controlled vocabulary values** (items, never entity kinds): `circa`; `male` and `female`; the participant roles `principal`, `partner`, `spouse`, `witness` and `officiant` (`object_has_role`, ADR-0035 §3.2); the kinship classes `kin_parent` … `kin_relative` and the sides `paternal` and `maternal` ([kinship guidance](LIFE_EVENTS.md#kinship-roles-and-other-life-assertions-adr-0014)); the civil statuses `unmarried` (never married), `married`, `widowed` and `divorced` (`civil_status`, ADR-0035 §3.1); and the five judgement note categories `judgement_kind`, `judgement_relation`, `judgement_date_reading`, `judgement_identity` and `judgement_other` (ADR-0035 §4). The kinship classes whose word is also a role's or a property's (parent, child, sibling, relative) carry "(kinship class)" in their labels, so that no two items share a label (the bootstrap's key) and none reads as the property of the same name.

Current birth, death and parentage conventions (ADR-0040):

- `birth` and `death` stay classes, for events a curator makes, but are kinds no extraction makes. Validation refuses an entity of either kind, and the GEDCOM adapter makes none. A birth and a death are statements on the person ("Living persons and privacy" below).
- The `parent` and `informant` roles are retired: `object_has_role` does not accept them and no prompt offers them; their vocabulary items stay.
- Step relationships use `kin_step_parent`, `kin_step_child` and `kin_step_sibling`.
- The qualifier `parentage` takes `parentage_birth`, `parentage_adoptive` and `parentage_foster`, labelled "birth (parentage)" and so on, since the `birth` class owns the label "birth" ([kinship guidance](LIFE_EVENTS.md#kinship-roles-and-other-life-assertions-adr-0014)).

**The relation decides the kind (ADR-0031, ADR-0035 §3.5).** Every item-valued property declares `accepts` in the manifest: the kinds its value may be (`location` a place, `carried_out_by` an organisation, `participant` a human or a family), each named exactly, so a subclass is accepted only where it is listed; or `any` (`depicts`), `subject` (the subject's own kind, for `said_to_be_the_same_as`) or `class` (`instance_of`, `subclass_of`). A list that names an entity kind also names `unclassified_entity` ([ADR-0013](EXTRACTION.md#schema-gaps-and-critique-adr-0013)). The manifest does not load when an item-valued property declares none. Validation refuses a claim whose value is of a kind its property does not accept, and extraction counts it among its rejects. An existing item named by its QID has no kind in a batch and is not checked. A vocabulary ref to a kind key (`human`, `place`, `time_period_class`, `photograph`) names the class, not an entity of it, so only `instance_of` and `subclass_of` take one, and they take no controlled-vocabulary value (`circa`); `depicts` (any kind) and `said_to_be_the_same_as` (the subject's kind) take no vocabulary item at all. An item value is thus an entity of the batch, an existing item named by its QID, or a vocabulary item its property names. Nor is an item value, a claim's or a qualifier's, ever the claim's own subject (the same local id, the same QID, the same vocabulary item, or a local ref resolved to the subject's QID): no property of the manifest takes its subject as its value, so Flörburg `location` Flörburg and Sebastian his own `father` are refused and counted among extraction's rejects. The claim is the unit of rejection: a qualifier naming the subject rejects its whole claim. The GEDCOM adapter leaves out a family's link that makes a parent their own child, and counts it (ADR-0036). (Amended by #461 and #462, 2026-10-05.) The writer checks the same rule again before its first write, since the identity map, an approved equivalence or a curator's correction of the equivalence sheet can put a claim's subject and its value, two mentions, on one item after validation: a father and a son of one name that clustering merges, with a `father` claim between them. A claim whose value or qualifier's value is then its subject's item is refused whole, nothing of it written, the rest of the batch written; the writer's result names it in `refused` and again in `self_references`, and the scratch write's record, the run report (`content.write.claims_self_referencing`) and the run-to-run diff count these apart from the writer's other refusals and from extraction's rejects. (Amended by #491, 2026-10-16.) A `time_period` claim from extraction is, for now, a counted reject: `time_period` accepts only a period, an entity of `time_period_class`, no entity kind offers one and no QID exists before write. `country_of_citizenship` accepts a place, since the place model has no country class; its description, which the chunk and single-pass prompts carry, says the value is a country, never a town, city or region within one, and validation does not tell them apart. The entity-manifest and chunk prompts name it among the relations of place, and the manifest gives the country a source states as a person's citizenship as a place entity, whether the source names it or gives only an adjective of nationality. A country given only by an adjective is labelled with the adjective as written (_an Australian citizen_ gives the place "Australian"), with the record status `adjective`, which keys nothing: the adjective is never turned into a name of the country, which would add a word the source does not write and pick one state where the source gives a nationality (ADR-0035, amended by #573). `part_of`'s list is flat for now: it takes a place or an artifact whatever its subject, so a place `part_of` an artifact passes the check, which reads the value alone.

**Reference properties** (`stated_in`, `inferred_from_extraction_run`, `judgement` and `judgement_note`) are marked `reference: true`: validation refuses them as a claim's or qualifier's property, and no prompt offers them. `offered: false` also keeps a property out of prompts while retaining it in the manifest and bootstrap; the scratch-run marks use this (`scratch_run`, `run_manifest_hash`, `identity_map_hash`).

**Document and placed subjects ([ADR-0039](ARTIFACTS.md#claims-about-artifacts-adr-0039)).** The seven document-subject properties describe the source itself, an artifact it places, a structured artifact record, an unclassified mention or an explicitly confirmed former record/mention. Every non-source form needs a supporting excerpt. `caption` separately takes a placed artifact and preserves one original-language passage; it requires no additional excerpt. Extraction cannot invent artifact-kind entities or classification claims naming artifact kinds, while structured/manual batches can supply them.

Validation and writing share `claims.subject_policy`; the writer adds registration and storage checks. The [artifact guide](ARTIFACTS.md#claims-about-artifacts-adr-0039) defines the forms, claim-specific confirmation provenance and support rules. Commands accepting `--placed` use verified common inventory, explicit compatibility records or supplied SHA-1 mappings; without that context, claims requiring placement refuse. Shared [source consumers](ARCHITECTURE.md#shared-source-consumers) preserve the inventory's owner and locator bindings.

**A retired property** stays in the instance and takes no new claim: it accepts nothing, validation refuses every claim of it, and no prompt that the manifest renders offers it. `spouse` is retired for new claims; [union modeling and reader compatibility](LIFE_EVENTS.md#adapter-and-reader-compatibility) describes its current replacement and the readers that still consume existing spouse statements. The GEDCOM adapter makes marriages and partnerships ([union adaptation](GEDCOM.md#unions-and-parentage)), so no batch carries a spouse claim. The writer refuses one itself, since `yizkr write` takes a batch without validating it: a claim of a retired property, or of a reference property, as its own property or a qualifier's, is refused before the first write, named in the result's `refused` list with a warning, and the rest of the batch is written (#410).

## Reference pattern (see ADR-0003)

The approved policy distinguishes historical assertions, curator attestations, derived results and operational metadata. Each needs provenance appropriate to it (ADR-0003). The current claim schema and writer still require source artifacts and implement the following encoding; broader provenance and history support follows the [ingestion contract](INGESTION_CONTRACT.md) and remains implementation work.

Historical statements on the current claims path carry a source reference with:

- stated in → artifact item (or artifact-fragment item)
- locator qualifier(s), where reliably known: page number and/or a region given as a percentage bounding box "x%,y%,w%,h%". IIIF canvas/region URIs are an optional future representation (ADR-0004), not an implemented requirement of the claim schema
- the printed page number, where there is one: the page number printed on the page the `page number` locator names, exactly as printed (`printed page number`, a reference property). The page number stays the physical page, the page's place in the media from 1, so a claim read from page 6 of _Our Family from Germany_, whose sixth page is printed as page 4, cites `page number` 6 with `printed page number` 4. The extractor sets it from the transcription record ([ADR-0037](SOURCE_READING.md#structured-vision-record-adr-0037)), never from the model: only for a claim whose page number is one physical page whose record gives a printed number. A range, a page given in words, a page the record gives no printed number and a transcription with no record (a text file's, a deck's slides) get none; none is ever guessed (#424). It describes the physical page: a page that shows a spread with one half numbered keeps that one number for every claim read from it, as both ways of reading a PDF give it the same ([ADR-0037](SOURCE_READING.md#validation-failure-and-attention)). The claims review sheet shows it in a `printed_page` column beside `page`, empty where the reference has none; like the other locators it is shown for checking and never read back, so a curator's edit to it is ignored (#449). A source that gives a printed page number gives its page number too: validation refuses one without the other, in a prepared claims file as in an extractor's batch. An excerpt's claims read the excerpt's own transcription, so they never take the printed number of the page that places it, and its `part of` the container keeps the container's physical page (ADR-0008)
- the source part, for a claim read from a PDF or PPTX or from an excerpt of one: one `source part locator` (a reference property) per structural placement of the part that supports the claim, or one for the part where it has none. Each is a compact JSON string naming the container's SHA-1, the inventory's source-part and placement identities, the part's kind and page or slide, and, when known, the digest of the reading it was located in. Extraction assigns it from the reading's located source context, never from the model; the inventory resolves it to the native part. A locator is never cut to the text limit. Repeated placements locate one source; they are not further witnesses
- optional short transcription excerpt supporting human verification, tagged with the language it is written in (BCP-47). The scratch driver takes each document's language from its transcription by default (`--language auto`, [ADR-0015](SOURCE_READING.md#language-selection-adr-0015)): from the transcription record the vision engine fills, which names the languages each page is written in ([ADR-0037](SOURCE_READING.md#structured-vision-record-adr-0037)), and otherwise by detection from the text outside its editorial marks. So a mixed-language folder tags each excerpt correctly; the extractor may still tag individual excerpts in their own language (a quoted passage in another tongue)

Machine interpretations on this claims path add a process reference:

- inferred from extraction run → extraction-run item
- with, where the claim carries a **judgement note** (ADR-0035 §4), `judgement` (the item of its category) and `judgement_note` (its sentence) beside it, in this run block alone: never in the `stated in` block, never as a qualifier, never on the run item. An entity's note, a kind or an identity call, goes in the run block of the `instance of` statement the writer writes, or adds a reference to, for its item. A note's sentence goes in NFC, on one line and cut at 400 characters as a locator is (below), and never refuses its claim; one that holds nothing the instance keeps, or a character Python's Unicode tables do not know, is left out with a warning, and its claim written without it, as every note is, with one warning, on an instance whose vocabulary lacks a note term. A curated claim has no run block, so no note. The write's result counts the noted run blocks it added (`notes_written`, #410), which the scratch write stage records for each document and the run report sums

A statement whose `sourcing circumstances` records what its source says of its own making (`machine-assisted`, ADR-0008, #666) adds a third reference: `stated in` the same artifact, with the page number, printed page number and transcription excerpt of the source's statement about how its text was prepared. It is the marker's evidence; the claim's own source block is unchanged.

On the claims path, a value asserted more than once, by several artifacts or by one artifact in several places (two pages, two passages, two regions of a scan), is one statement for each set of qualifiers. It carries a `stated in` reference for each place, with that place's locators and excerpt, and the run reference of each run that added one, one block for each of its notes (and one without a note, where a claim of the run gave none); writing a batch again adds no reference (#335). The run block is compared whole, with its note: a second claim of the same run on the statement adds its own run block where its note differs, so one statement can carry several blocks of one run, and a reader counts runs by run item, never by blocks. A claim from a place the statement already cited before the write adds its run block only when it carries a note, or when a noted claim of its run gave the statement a block of that run, in this write or an earlier one. A statement is compared as a curator's when it was one before the write and still is: a machine claim of the write that joins a curator's own write at normal rank makes it a machine one for every claim of the write, while one whose rank a curator changed stays a curator's. The artifacts it cites for that comparison (below) and the places it cites are read as it stood before the write, and a claim that adds nothing is looked at again once the batch's other claims are written and its kinds recorded, so a run's noted and note-less claims, and a curator's claims beside machine claims, from one place or several, give the same blocks in whatever order the batch gives them, for the run that wrote the statement and for a later one, and a later run's note-less claims alone add nothing there (#410). An entity's kind takes its run blocks by the same rule. No block is edited to add or remove a note. The exception is a statement with no run reference (a curator's own write, until a machine claim of this write or an earlier one joins it) or whose rank a curator changed: the writer adds nothing to it for another place of an artifact it already cites (the writer's module docstring, `src/yizkr/pipeline/writer.py`, gives the rule). The kinds and type hints the writer records after the claims, from an entity manifest or a ref, follow [ADR-0007](EXTRACTION.md#entity-first-and-chunked-extraction-adr-0006-adr-0007) instead.

Wikibase holds at most 400 characters in the text of a string, external-id or monolingual text value, a reference's page number, printed page number and region among them, and no text value with a line break or a tab in it, or whitespace at either end; it refuses the whole edit that sends a text it does not hold. It also cleans a text up, making each C0 control character but the tab, the line feed and the carriage return, and each of the noncharacters U+FFFE and U+FFFF, U+FFFD: in a string or external-id value before it checks and stores it (so it changes a vertical tab or a form feed there, and refuses one in monolingual text), and in every text its API gives back, monolingual text included. The writer checks each text in NFC, the form the instance keeps it in, and sends none that the instance would give back changed (#366, #384, #403). A page number, printed page number, region or excerpt goes on one line: whitespace at either end is dropped, a line break inside becomes " | ", a tab a space and each other character the instance cleans up U+FFFD, as the instance gives it back, so a re-run finds its reference block; one of whitespace alone is left out. One still over the limit is cut at a break between words and ends with " … sha1 " and the first 12 hex digits of the SHA-1 of the whole text: a locator only places the claim in its source, as an excerpt only helps a reader check it there, and the digest keeps two places whose locators or excerpts agree up to the cut two references. A claim whose own text, its value or a qualifier's, is over the limit, or holds a line break or a tab, or has whitespace at either end, or holds a character the instance cleans up, or holds a character Python's Unicode tables do not know (above; its page number, printed page number, region or excerpt holding one refuses it too, #431), is refused, never cut, trimmed or cleaned up, since that would alter what the source says: nothing of it is written, and the write's result names it by its claim id (its review-sheet id, unless the review corrected it), with a warning that says why (the writer's module docstring). Every other claim of the batch is written. An entity's type hint is free text, compared ignoring its spacing, so it goes with each run of whitespace in it as one space, and each character the instance cleans up as U+FFFD, and a re-run finds the statement written for it.

The current writer's curator-attributed statements (a value correction from the review CSV) carry the `stated in → artifact` reference only: the human decision is recorded in the reviewed artifact and MediaWiki edit history, rather than a machine run block. The pipeline marks these with the claim contract's `curated` flag, which only the review sets: an extractor drops the flag, and any row approval, from a model's answer, so every claim a model gives is written with its run reference.

The pipeline's claim JSON contract implementing this pattern is `src/yizkr/claims.py` (`ClaimBatch`): sources are required fields there, ranks are unrepresentable, and property/item references use manifest keys resolved to local ids only at write time. A claim cites its source artifact by content: the SHA-1 of the artifact's media (`ArtifactRef`, see _Artifact identity_ below), which holds across instance resets. It is the only form a source takes: a batch whose claim names its artifact item by QID does not load (#102). The writer resolves the hash to the artifact item carrying that `media SHA-1` at write time, and refuses a batch that cites media no item carries before it writes anything. So an artifact a claim cites has media: a page fragment is cited through its artifact and a `page number` locator, and an un-held GEDCOM media item (below) is never a claim's source. Every producer names the source itself: an extractor sets each claim's source to the key of the document it read, whatever the model wrote there; the GEDCOM adapter cites the export's bytes; and a face proposal cites the photograph's bytes, while its subject stays the photograph's item. No transcription and no extraction prompt names an artifact by QID: a transcription names its artifact by the same key, and the extraction prompts name it by that key and ask the model to cite it (#127), so a reset, which gives each artifact a new QID, changes neither.

Ordinary identity-map writes append identity provenance to the source-backed `instance of` statements of materialized entities. If a local reference supplies no supported kind, an operational `identity record` statement carries its origin instead, without asserting a historical type or source claim; a later sourced kind preserves this earlier link. An `identity record` reference gives the method, cluster ID and immutable record digest; the record carries the map decision hash, original producer facts when available and an explicit unratified marker. The method describes entity placement, separately from the source’s kind assertion and the extraction run. These references do not grant durable assignment acceptance or human confirmation. Accepted origins and confirmations remain separate references, and later acceptance preserves earlier map evidence. See [identity review](IDENTITY_REVIEW.md) for publication, recovery and graph-only querying.

Later-cohort creations initially carry reviewed display terms only. An immutable creation authorization links the original `new_entity` approval, source occurrence and interpreted identity to the exact creation payload and receipt. That interpretation participates in candidate blocking as operational context, not as a historical assertion. The initial accepted assignment retains the creation decision. Both existing-target and newly created assignments publish an operational `identity record` link, with explicit reviewed-assignment/creation origin separate from human confirmation; historical kinds and other claims require their own review.

## Correction and review

The current contract permits audited correction, supersession and retraction of erroneous interpretations, duplicate representations and attribution mistakes while preserving genuine source disagreement. It distinguishes approval to retain from approval to publish. Bounded sets of ordinary assertions may be approved together; identity changes must be explicit in the review, and existing-entity merges/splits and face associations require affirmative confirmation.

The writer adds claims and references and respects curator ranks. Review CSVs can correct proposed claim values and resolve approved equivalences, but they do not supply a general retained-state correction interface. The assignment-aware route records each attributed assertion's subject/object/qualifier assignment revisions and actual statement GUID/source-reference hashes, including support already present on a shared statement. These receipts expose the affected support for future correction; they do not authorize removal or movement of other sources. Unchanged approvals survive compatible source correspondence and unrelated additions; materially changed content, attribution or assignments require scoped review. Retraction and split remain under #142.

## Artifacts and registration

Held media are wiki files; the artifact's `media file` property names the file and `media SHA-1` identifies its canonical bytes. [Registration](ARTIFACTS.md#registration-and-held-media-adr-0010) uses a unique lag-free hash match and verified creation binding, never a title, and recovers interrupted creation before dispatching another item. It preserves curator terms and ranks, checks revisions, and refuses ambiguity. Wiki files are never overwritten; changed bytes use a content-tagged filename.

Page fragments require a typed parent/page structural match, not a shared label. Container registration preserves original-part composition and actual placements; unplaced resources gain no guessed page. The artifact guide owns filename/term handling, label-side safeguards, collision alerts and unheld-media distinctions.

Registrar statements use the source/composition references appropriate to their current encoding. Source and run self-references can require creation before completion of those statements; the creation registry preserves the same item across that interruption. This implementation does not require historical artifact citations for all operational metadata. Source registration precedes historical writing and approves no historical claim. Retained text-source registration requires explicit confirmation.

- **A run item states its kind in a second write.** Its `instance of → extraction run` cites its own QID. The initial item creation therefore precedes its self-reference. Resume verifies the operation’s creation binding, even after a display edit, and completes any missing kind or run marks on that same item. Existing curator ranks remain unchanged. The extraction and place-hierarchy paths share this recovery mechanism; a matching run label without a binding requires verified migration.
- **A scratch run marks its run items** (#200; ADR-0025 §1). The run item of each batch a scratch run writes states, in the same second write as its kind and stated in itself, `unratified scratch run → <run id>` (the run that wrote it: nothing it backs is ratified, reviewed or confirmed, and the next reset discards it), `run manifest hash →` the SHA-256 of the settings its run manifest records, and `identity map hash →` the SHA-256 of the identity map the batch was written with. The three are string properties of a run item alone, marked `offered: false` in the manifest, so no prompt offers them: the extraction prompts list only the properties a claim may use, and the critique prompt only those the manifest offers (decision EZ), so every prompt is as it was, byte for byte. A run item found again lacking one gains it; one it states already, at any rank, is left as it is. The LAN site reads them: when any run item states `unratified scratch run`, every page's header says the instance holds a development-stage scratch run and names it.
- **A scratch run writes unattended** (#200; ADR-0025 §1, §2). Its write stage takes every claim of each document's batch, with no review and no approval file, at normal rank, with both references, through the run's one identity map, on an instance the run reset itself; depicts claims are left out of what the writer is given, and counted in the run report, so no scratch run writes a depicts statement (ADR-0005). Each claim's write has the edit summary `scratch run: write unratified claim`, and each artifact's description names `yizkr scratch run` as what ingested it.
- Machine-proposed entities (people, places) get their `instance of` statement referenced to the artifact that mentions them. A later source that names the entity adds its own references (the artifact and its extraction run) to that statement, or, when it gives a different kind, a statement of its own: the kinds different sources give coexist like any other attributed values (ADR-0002, [ADR-0007](EXTRACTION.md#entity-first-and-chunked-extraction-adr-0006-adr-0007)). A `type hint` accumulates the same way, compared as free text.

## Artifact identity (see ADR-0010)

Distinguish original bytes, structural source parts, canonical source owners and generated reading representations. A verified owner/part binding survives re-encoding of its reading representation. Equal prepared pixels, titles or similar-looking newly supplied files do not establish historical equivalence. [Current ownership and registration rules](ARTIFACTS.md) require verified bindings; general near-duplicate/version review remains [#162](https://github.com/WillHirsch/yizkr/issues/162).

Eligible held sources are registered from verified bytes, with exclusions checked before instance access or upload. Filtering an excluded embedded image from its independent reading/registration does not redact the original container: the eligible container file is uploaded unchanged. [Model-input exclusion checks](LLM_CACHE.md#pdf-model-input-exclusions) separately guard composed visual reading.

## Artifact coverage — cross-domain relations (planned)

Artifacts do not only assert claims about people and events; they also _cover_ regions of other domains: a map covers a geographic extent, a census page covers a district on a date, a letter spans two places. These cross-domain coverage relations (cf. Dublin Core "coverage") are ordinary statements on the artifact item, and the reference requirement (ADR-0003) applies unchanged: what an artifact shows about itself is referenced `stated in → the artifact itself` (the registrar convention above); coverage computed by a tool (e.g. georeferencing software) adds an `inferred from extraction run` reference like any machine write.

Planned first instance — **georeferenced map artifacts**:

- a `map` subclass of artifact;
- two globe-coordinate properties on the map item, `bounding box north-west corner` and `bounding box south-east corner` (an axis-aligned extent; Wikidata's extremum-point properties P1332–P1335 are the nearest semantic precedent), so interactive maps (R6) can draw the artifact's outline in place and SPARQL can answer "which artifacts cover this place?";
- W2 upgrade path: IIIF Georeference annotations (Allmaps-style ground control points) refine the flat bounding box exactly as IIIF canvas+xywh URIs refine percentage regions (ADR-0004) — the corner properties then remain as a cheap derived summary for query and display.

Other domains follow the same shape rather than inventing new machinery: temporal coverage (the period a map _depicts_, distinct from when it was made) reuses `time period` / date properties, and subject coverage uses `main subject`; who or what a source says an image shows is `shows`, whether stated by the image itself or a supporting passage in its container. `depicts` is the faces flow's confirmed depiction (ADR-0005). [Artifact claims](ARTIFACTS.md#claims-about-artifacts-adr-0039) retain the source that states each assertion and its process provenance. Prefer an existing Wikidata-mirrored property and keep values structured.

## Compound artifacts (see ADR-0008)

PDFs and PPTX presentations share one [container-source model](ARTIFACTS.md#container-sources-adr-0008). Native text, shapes and speaker notes belong to the container. Every original embedded image is independent, including full-page scans, small pictures, backgrounds and unplaced resources. Generated page/slide renders are reading representations, not new witnesses. Size and page coverage affect reading strategy, never ownership.

The persisted inventory separates original parts, occurrence-specific placements, canonical owner bindings and generated representations. Repeated placements share an established owner while retaining their locations; unplaced resources have source-part locators without invented page numbers. Page fragments locate content within the container. [Container architecture](ARCHITECTURE.md#container-inventory) and [shared consumers](ARCHITECTURE.md#shared-source-consumers) describe the products and their use.

Independent images retain their own readings. A reading whose pages are all blank or not document pages produces no excerpt; an illegible document reading remains visible as an excerpt. A proved sole-image PDF page reads that image once and leaves a parent marker, without duplicate claims. Composed readings that cannot separate source owners remain incomplete for attribution. [Source reading](SOURCE_READING.md#pdf-reading-limits) records PDF limitations; whole-slide PPTX vision remains [#747](https://github.com/WillHirsch/yizkr/issues/747).

A container can supply a verbatim caption and structured facts about an image, each attributed to the container with its supporting location. The image can supply its own independent assertions. Verified contextual readings can assist interpretation, but assertions found only in another source cannot become the target's evidence. [Claims about artifacts](ARTIFACTS.md#claims-about-artifacts-adr-0039) defines these distinctions, the subject forms and display/export behavior.

Machine-assisted preparation is an existing sourcing circumstance. A source's explicit preparation statement supplies its scope and separate evidence; the pipeline marks applicable claims and reports unresolved scope. It does not infer the marker from style or copy a container's marker onto its images' claims. [Extraction](EXTRACTION.md#completion-diagnostics-and-reuse) owns this processing rule.

## Faces and depiction (see ADR-0005)

- A face identification links the photograph item to a person with `depicts` and the qualifier `relative position within image = "x%,y%,w%,h%"`. Detection or manual marking creates a region; matching proposes identity. Each association requires affirmative human confirmation. Several displayed associations may be confirmed together, but generic document/run acceptance must not confirm faces.
- Current commands are `yizkr ingest detect-faces`, `enroll-face` and `match-faces` (`pipeline/faces.py`). They produce proposals for the shared review flow. Enrollment supplies a gallery example, not confirmation of later matches.
- The current CSV implementation requires a per-row approval and refuses bulk acceptance for `depicts`. `apply_review` records `row_approval`, binding the claim and the manifest records of its local references. The writer validates it before instance access. This digest is batch review state, not an authenticated curator signature or a durable graph-revision binding; the [ingestion contract](INGESTION_CONTRACT.md) defines the target boundary, implemented through #130 and #142.
- The statement references the photograph and region plus the detection run for a machine proposal. The reviewed batch and edit history record the confirmation action. Source/run references alone are not a complete account of the human decision. Rebuild runs omit `depicts` entirely.
- **Associated media vs. depiction ([ADR-0021](GEDCOM.md)).** `image` links a person to a medium a source associates with them, such as a portrait or obituary scan. The GEDCOM adapter emits it for OBJE records as un-held media items of kind `artifact`, with neither `media file` nor `media SHA-1`. It does not fetch the referenced bytes. The `image` claim is undated; an object's own DATE becomes its media item's `inception`, with the source's precision and bounds. Acquiring media is a separate authorized step and uses content-keyed artifact registration.
- **Source wording vs. confirmation ([ADR-0039](ARTIFACTS.md#claims-about-artifacts-adr-0039)).** `shows` records whom a source says an image shows, from the image's inscription or a container's supporting passage. `caption` records a container's verbatim words about the image. Neither is a confirmed region-to-person association or maps to `depicts`. Any use of those words to propose a face match still needs the confirmation gate.
- IIIF annotations, photo-service integration and XMP/MWG export are optional follow-ups (ADR-0004, ADR-0005), not implemented substitutes for this gate.

[Life events and relationships](LIFE_EVENTS.md) is the current guide to person birth/death assertions, [unions and their events](LIFE_EVENTS.md#unions-and-their-events-adr-0036), [kinship and participant roles](LIFE_EVENTS.md#kinship-roles-and-other-life-assertions-adr-0014), parentage, residence and persecution/displacement events. ## Identity and reconciliation

The contract separates source bytes, placements, readings, local mentions and persistent entities. Labels, filenames and clustering output are not durable identity. [Matching guidance](MENTIONS_AND_MATCHING.md#matching-candidates-and-structural-exclusions-adr-0017) describes current name keys, structural filtering and corpus-clustering limits. Structural exclusions depend on supplied facts and can be mistaken; graph matching does not prune candidates for date disagreement.

[Durable identity review](IDENTITY_REVIEW.md) provides recorded later-cohort matching, explicit assignments, correspondence, protected additions and approved historical-claim application. A new equivalence requires review; merges/splits of existing entities require affirmative confirmation and a supported correction workflow. Current correction limits remain under [#142](https://github.com/WillHirsch/yizkr/issues/142). Legacy map calls retain their one-map restriction, and disposable rebuilds can use unratified machine assignments without conferring human confirmation.

Where a source supports an equivalence between two existing items, it can be recorded as `said_to_be_the_same_as` (Wikidata P460), with source and applicable process provenance. That statement does not execute an item merge. A place-distinctness verdict likewise creates no containment assertion; any such assertion needs its own supporting source.

## Contradictions

Preserve genuine source disagreement without requiring a canonical answer. A preferred rank does not make competing normal-rank evidence disappear. Machine alternatives and corrections are not independent historical witnesses; the [correction contract](CONTRACT.md#evidence-interpretations-and-correction) governs how they differ from source disagreement.

The private site's disagreement report compares selected, attributed readings across artifacts. It fetches statements, derived-death inputs and place containment separately, then compares them in Python. This is a selective view, not a validator of all retained history: same-artifact conflicts, legitimate multi-valued assertions, date resolution, parent sets and containment each affect what it reports. [Disagreement comparison (ADR-0033)](../src/yizkr/queries/README.md#disagreement-comparison-adr-0033) owns the compared properties, attribution rules, current limits and query interfaces.

## Living persons and privacy (see ADR-0020)

Archive data and exploration are private by default. Retaining or displaying evidence grants no publication permission. The non-privileged export is a filtered view, not a public-safe archive: retained text can still name living people. Final privacy and cutoff decisions remain under [#70](https://github.com/WillHirsch/yizkr/issues/70) and [#72](https://github.com/WillHirsch/yizkr/issues/72); a public site requires separate authorization under [#163](https://github.com/WillHirsch/yizkr/issues/163).

[Runtime privacy (ADR-0020)](PRIVACY.md) owns the implemented person-selection rules, 123-year default cutoff, birth/death evidence checks, private-site badges and additional export exclusions. There is no stored living flag or universal human-confirmation gate. The site shares the person-evidence predicate but does not apply the export's whole structural filter. Unsupported dates or an inconsistent query-service snapshot can refuse the filtered export while preserving other completed backup products.
